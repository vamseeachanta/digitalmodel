Require real numerical and saved-result evidence from the OrcaFlex smoke

Issue 2082 · T2 · Client: N/A · Lane: Codex · Mode: parallel read-only planning, isolated implementation after approval

Objective and deliverable

The repair will make the existing OrcaFlex smoke return success only after a one-thread solve produces finite results, completes dynamics and reloads its saved simulation successfully. It will supply a bounded prerequisite for future credentialed-task and Linux-producer acceptance. It will not certify a production lane or an engineering design.

The broader ecosystem will retain two objectives: reliable execution from enrolled producers through the licensed worker, and reusable model-family qualification across OrcaFlex and structural FE adapters. This issue will address only the immediate smoke-proof gap.

Bounded design

  1. Every OrcaFlex model constructed by the probe, including data/simulation readers, will receive threadCount=1. The success report will record the observed model.threadCount property after solve or loading, as applicable; a mismatched count will fail. This will constrain this probe only, not all managed jobs or the batch executor.
  2. Static effective tension will be converted and checked for finiteness before it enters the report. Dynamics will require simulationComplete and the expected stopped state; a paused/incomplete model will fail even if some samples exist.
  3. The selected dynamic history will contain at least two samples, all finite. This will be a smoke-data sanity requirement, not a convergence criterion. Empty, one-sample and nonfinite histories will fail with a readable stage/reason.
  4. The probe will preserve the existing data-file load check, save the simulation, and require a nonempty saved file. It will create reader = OrcFxAPI.Model(threadCount=1), call reader.LoadSimulation(sim), retrieve reader["SmokeTestLine"] and confirm completed dynamics plus finite readback using TimeHistory("Effective Tension", OrcFxAPI.Period(1), OrcFxAPI.oeEndA). Loader exceptions or failed postconditions will fail the probe. It will compare sample counts. It will not invent a numerical equality tolerance or claim bitwise equivalence across serialization.
  5. Small helpers will separate numeric validation and save/reload proof while retaining check_orcaflex(work_dir) and the existing solver/ok result contract. New proof fields will be additive. Model and line references will be initialized before the guarded body and cleared in finally, with line references cleared first. No undocumented model close method will be assumed; native destruction will follow the API's Python object-lifetime contract. Callers will keep existing scratch cleanup.
  6. Failure reports will contain no numeric NaN or Infinity. Values will be validated before insertion; error details will remain text. Strict JSON serialization with json.dumps(report, allow_nan=False) will be a test oracle for the OrcaFlex-only report. The generic AQWA result writer and its contract will not be broadened by this issue.
  7. The engine workflow will keep writing its diagnostic report before raising when require_all=true. Explicit require_all=false will preserve normal return with ok=false for diagnostics; it will not become production acceptance. The run_probes(include_host=False) default will retain hostname privacy.

Additive report contract

Success will include integer thread_count_requested=1; thread_counts_observed, an object with integer solve, data_reader and simulation_reader values; booleans static_finite, dynamic_finite, simulation_complete, saved_sim_reloaded, reloaded_simulation_complete and reloaded_dynamic_finite; and integer reloaded_dynamic_samples. Existing sim_bytes will remain the positive saved-file size. On failure, proof fields will appear only after observation; import or constructor failure will never fabricate an observed thread count. Numeric validation will use math.isfinite(float(value)), with no magnitude plausibility threshold. Fake-API acceptance fixtures will use pytest monkeypatch to inject and restore the module and will record independent simulation-reader calls and results.

Proposed flow

construct model(threadCount=1)
configure existing generic line and environment
calculate statics → validate finite scalar → record
run dynamics → require complete/stopped → validate history → record
save data → validate data loading with explicit thread count
save simulation → require nonempty file
fresh model(threadCount=1) → LoadSimulation → find expected line
require complete/stopped → validate restored history and sample count
return ok=true with additive proof fields
on any error → release references → return ok=false with safe diagnostics
workflow → write report → preserve existing require_all behavior

Native acceptance and operational boundary

The native harness will require Windows PowerShell 5.1 or later on the licensed Windows host with OrcaFlex 11.6c. Linux will run offline checks and submit future managed requests; native acceptance for this issue will run on Windows.

After offline checks and code review, the implementing agent/operator will explicitly run the proposed docs/plans/evidence/issue-2082-native.ps1 harness, passing the existing solver Python and reviewed checkout as parameters. It will invoke scripts/solver_smoke_test.py --solver orcaflex --json --output-dir <owned-scratch> in a fresh scratch directory. A 90-second harness deadline will bound the process; timeout cleanup will target only its owned process tree and retain failure diagnostics. A fake child-process fixture will verify timeout/cleanup behavior before any native invocation. Successful acceptance will require the new finite, completion, thread and saved-simulation proof fields. Ordinary tests and CI will never acquire a licence.

The proof will record exact revision, Python/DLL versions, time, result and input/output hashes. It will preserve the live checkout, environment and scheduled tasks. The direct in-process API will not gain a hard timeout guarantee in this issue; managed execution will continue to require the outer lane's reviewed deadline and cleanup contract.

Separate deployment work will still require an approved neutral scope, explicit effective policy, task cutover, host-level arbitration and credentialed-task/Linux-origin tests. This issue will neither enqueue nor activate those operations.
