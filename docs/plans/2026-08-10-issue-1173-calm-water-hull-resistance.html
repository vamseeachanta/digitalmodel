#1173 implementation plan: calm-water hull resistance by interFoam towing

Issue #1173 · branch plan/1173-calm-water-hull-resistance · base 2a6b521e · revision 1 · status: awaiting user approval

The framing this plan was commissioned under is wrong in one load-bearing respect, and correcting it changes the recommendation. The premise was that the repository has zero resistance capability, evidenced by a whole-tree grep returning nothing. That grep was git grep -i 'resistance|holtrop|froude|wave.making|calm.water' — no -E, so | is a literal character in a basic regular expression and the pattern searched for one long nonsense string. Re-run with -E it returns 30+ files, among them a complete Holtrop-Mennen implementation that has been in the tree since May. The empirical method the sequencing question was about is already written. What it lacks is a gate, and that changes what #1682 costs and therefore how it sequences.

Goal and authorization boundary

Produce a calm-water ship-resistance capability: a hull towed at constant speed through a free surface by interFoam, with the total resistance coefficient Ct extracted from a forces function object on the hull patch and gated against published towing-tank data.

  • G1 — an emitted, runnable resistance case that reaches a converged force on the pinned OpenFOAM v2312 toolchain, not merely a structurally valid directory tree.
  • G2 — Ct at a stated Froude number within a stated tolerance of a stated published dataset, asserted in a test that can fail.
  • G3 — the wave-making trend across Froude number reproduced, so that a single lucky point cannot pass the gate.
  • G4 — an independent empirical cross-check, so a converged-but-wrong answer has a second chance to be caught.
  • G5 — the CaseType reuse-vs-new decision documented and defended (an explicit acceptance criterion of the issue).

Boundary. This plan does not touch seakeeping, added resistance in waves, self-propulsion, propeller or rudder modelling, or full-scale extrapolation to delivered power. The body is fixed — no free sinkage and trim in the primary deliverable (see Risks). It does not attempt to fix #1192's flat-plate and cylinder cases, though it is shaped by why they failed.

The decisive find: OpenFOAM v2312 ships a complete, maintained, calm-water ship-resistance case, and it is already decomposed for exactly eight cores. $FOAM_TUTORIALS/multiphase/interFoam/RAS/DTCHull is a towed Duisburg Test Case container ship: snappyHexMesh from an STL, interFoam, a forces function object on the hull patch, half-domain with a symmetry plane. The tutorial is pseudo-steady, which is the difference between feasible and not

system/fvSchemes:   ddtSchemes { default localEuler; }        <-- LTS, not transient
system/controlDict: endTime 4000; deltaT 1; writeInterval 100
system/fvSolution:  maxCo 10; maxAlphaCo 5; maxDeltaT 1;
                    nOuterCorrectors 1; nCorrectors 2;
                    momentumPredictor no; MULESCorr yes;
system/snappyHexMeshDict: maxGlobalCells 2000000; nCellsBetweenLevels 3;
                    refinementSurfaces { hull { level (0 0); } }  addLayers true; nSurfaceLayers 3;
system/decomposeParDict:  numberOfSubdomains 8; hierarchical; n (2 2 2);

localEuler is local time stepping: each cell advances on its own pseudo-time towards a steady state. The run is 4000 pseudo-iterations at interface Courant 5, not a transient integration Courant-limited to milliseconds. A naive transient estimate for this problem lands near 5 600 real time steps at Co = 0.5; LTS with maxAlphaCo 5 is roughly an order of magnitude cheaper for the same converged force. Every wall-clock figure below assumes LTS, and adopting LTS is a requirement of this plan, not an optimisation.

In-repo prior art: a Wigley LTS run already happened, and its cost was recorded

docs/domains/openfoam/case_studies/wigleHull_LTS/wigleHull_LTS.md is a troubleshooting log from a manual Wigley interFoam LTS run: "Current runtime: 6 hours using 4 processors", solution written at iteration 5000, inlet Umean 1.452, outlet outletPhaseMeanVelocity — the same boundary condition family as the DTCHull tutorial, so this was almost certainly derived from it. 24 core-hours is a measured anchor for a Wigley-class LTS resistance run, and it is the only in-repo wall-clock datapoint for this problem class. The directory also holds wigley_hull_coefficients.ods and coeffs_convergence.png. It contains no case files, no mesh and no geometry, and it carries hardcoded developer paths — it is a narrative, not a reproducible artifact, and it cannot be the basis of a gate.

The existing case builder cannot emit this case, and #1192 says why that matters

OpenFOAMCaseBuilder.build() (src/digitalmodel/solvers/openfoam/case_builder.py) writes controlDict, fvSchemes, fvSolution, blockMeshDict, decomposeParDict, setFieldsDict, transportProperties, turbulenceProperties, g, dynamicMeshDict and the 0/ fields. It does not write snappyHexMeshDict or surfaceFeatureExtractDict, does not stage an STL into constant/triSurface/, has no hull wall patch in its hardcoded inlet/outlet/bottom/top/sides boundary block, has no function-object hook other than a pressure-tap-specific one, and SolverConfig.to_control_dict() emits no maxAlphaCo or maxDeltaT. BoundaryType lacks slip, symmetryPlane and fixedFluxPressure.

#1192 is the cautionary precedent and it is still open. The Phase-2 foundational cases (#1167 flat plate, #1166 cylinder) were built by driving this generic builder with a custom DomainConfig. The mesh built; the solver diverged at iteration 1. The issue's own root-cause note is that the generic builder emits boundary patches that do not match the physics. A laminar flat plate is the simplest case in the family. A 3D two-phase VOF towed hull with a snapped body-fitted mesh is the hardest. Any plan that reaches #1173 through the generic builder is planning the same failure at ten times the cost.

The repository already contains the counter-pattern. Of the eleven registered validation cases, ten bypass the builder entirely and write frozen, verified literal dictionary templates with @TOKEN@ substitution (validation/flat_plate.py, dam_break.py, wave_tank.py, kleefsman.py, maccamy_fuchs.py). Only cylinder.py goes through the builder, and its own docstring concedes the generated mesh is "a plain box without the cylinder body" — which is precisely the case #1192 reports as unrunnable. The literal-template flavour is the pattern that works, and it is what this plan adopts.

validation/cylinder.py:147 also records the standing decision on the enum: "No new CaseType is introduced: the routing layer owns the enum, so we reuse CaseType.VIV." That is directly relevant to G5.

Dispatch, work root and evidence conventions already exist

  • scripts/setup/dispatch-cfd-run.py — run from the orchestrating box, SSH-probes candidate hosts for cores and load, selects one, sources the v2312 etc/bashrc, and runs a remote command with CFD_DISPATCH_HOST/CFD_DISPATCH_RANKS exported. --max-load-per-core is fixed at 1.5, --oversubscribe is forbidden, and --dry-run with --assume-probe plans offline.
  • External work root (#1565, a T3 plan with two rounds of three-provider review) — heavy cases live outside every git checkout under an operator-private root, keyed by a RunIdentity SHA. Hosted mode forbids YAML from naming the root at all.
  • Result policy — only cases.csv and batch_summary.json come back input-local, with host paths redacted. Committed evidence lands in docs/api/cfd/; there are already nine *-verification.html reports there plus JSON manifests.
  • checkMesh verdict rule: exit code zero is insufficient. Output must contain Mesh OK and zero Failed N mesh checks. This will bite on a snapped hull mesh and is an explicit stage gate below.

Does #1682 gate #1173?

The question was to argue this from #1173's own validation-gate requirement rather than from convenience. Doing so gives a split answer, and the split matters more than either half.

It does not gate the primary gate, for a physical reason

#1173's gate is against towing-tank data at model scale. Holtrop-Mennen predicts full-scale ship resistance: holtrop_coefficients.py hardcodes RHO_SW = 1025.0 and NU_SW = 1.1892e-6 (seawater), and total_resistance adds RA, a model-ship correlation allowance whose entire purpose is to absorb the full-scale extrapolation error that a model-scale computation does not have. Evaluating it at model Reynolds number in fresh water, with CA included, is a category error. So Holtrop-Mennen cannot be the reference the gate is measured against, and #1173's primary acceptance criterion is not blocked by #1682 in any form.

It does gate the defence against the failure mode this issue is most exposed to

The stated worry is real and this repository has closed issues over it: a converged CFD result carries no internal signal distinguishing right from wrong, and matching one number to one number cannot separate a correct solution from one with compensating errors. Two independent defences exist, and only one of them is cheap:

  1. Multi-point falsifiability — reproduce the shape of the Ct(Fr) curve, not one point. Costs one extra solver run per point. Specified below and it is the primary defence.
  2. An independent empirical estimate of the wave-making component. Holtrop-Mennen's wave_resistance returns RW alone, without CA and without the friction term. Under Froude similarity the wave-resistance coefficient is scale-independent, so Cw from Holtrop-Mennen is directly comparable to the residuary coefficient the CFD produces at model scale, with no full-scale extrapolation in between. That check costs milliseconds and the function already exists.

But defence 2 is only worth having if wave_resistance is itself trustworthy, and today nothing in the test suite constrains it beyond assert rw >= 0.0. Using an unvalidated empirical method to validate a CFD result does not add a check; it moves the unverified claim one level down and makes the stack look better-defended than it is. That is the same failure shape as the fixture that no test loads.

Position: #1682 and #1173 run in parallel, with a one-way dependency of #1173 on a narrow slice of #1682 — and the slice is small precisely because the recon premise was wrong. The slice is not "implement Holtrop-Mennen"; that is done. It is: make test_holtrop_mennen.py load its own fixture and enforce the declared 15% band, and add a KCS case to that fixture. Estimated half a day. It lands as Stage 0 of this plan's sequence and is offered back to #1682 as its residual scope. If the owner prefers to keep that work wholly inside #1682, Stage 0 becomes a hard blocker on Stage 5 and nothing else in this plan moves.

The hull choice is entangled with this and pushes the same way. Holtrop-Mennen is a regression over conventional merchant hulls. KCS (Cb 0.6505, L/B 7.14, B/T 2.98, bulbous bow) sits inside that basis. A Wigley hull — wall-sided parabolic, L/B 10, B/T 1.6, no bulb, no transom, Cb near 0.44 — sits well outside it, and Holtrop-Mennen applied to a Wigley returns a number with no standing. Choosing Wigley does not merely weaken the cross-check; it removes it, and leaves multi-point falsifiability as the only defence.

Hull choice

Three candidates, not two. The issue proposes Wigley or KCS; the recon adds DTC, which arrives with a working case attached.

The cost intuition in the brief does not survive contact with the numbers

The framing offered was "Wigley: cheap mesh, weak data; KCS: expensive mesh, excellent data." The second half holds. The first half does not, and it is worth being explicit about why, because it changes the decision.

Cell count in a free-surface resistance case is set by resolution per wavelength and per wave height in the Kelvin field, and by the boundary-layer treatment on the hull. It is not set by how geometrically complicated the hull is. The fundamental transverse wavelength is λ = 2πFr²L, so it scales with hull length exactly as the hull does — a shorter hull buys a proportionally shorter wave and no cells. Evidence on both sides:

  • A published interFoam Wigley study used ~6M cells at y+ ≈ 2 (wall-resolved).
  • A KCS study using a wall-function treatment (y+ 38–77) reached ±2.43% on Ct with 0.40M half-domain cells.

The 15× spread is a modelling choice — wall-resolved versus wall-functions — not a hull property. Wigley is not meaningfully cheaper than KCS at equal turbulence treatment. The in-repo Wigley LTS run cost 24 core-hours, which is the same order as the DTC estimate below.

Cost estimate, and how it was derived

Two independent anchors, agreeing to within a factor of two.

Anchor A — in-repo measured (wigleHull_LTS.md)
  6 h x 4 procs = 24 core-h, ~5000 LTS iterations, Wigley-class mesh
  => ~2.5e-5 core-s per (cell x iteration) at an assumed ~0.7M cells

Anchor B — DTC tutorial as shipped
  2.0e6 cells (snappy cap) x 4000 LTS iterations x 2.5e-5 core-s
  = 2.0e5 core-s = 55.6 core-h
  on 8 cores at ~85% parallel efficiency  =>  ~8.2 h wall-clock

KCS 1/31.6, half-domain, 2.0-2.5M cells, 4000-6000 iterations
  =>  8-16 h wall-clock per Froude number on 8 cores
  x 3 Froude numbers  =>  1-2 days of gpu-claw, plus meshing

KCS is not impractical at 8 cores. The reason is LTS: a transient interFoam run of the same mesh would be roughly an order of magnitude worse and the honest answer would flip. This estimate is a plan input, not a result — Stage 1 exists to replace it with a measurement, and the plan's schedule is allowed to change when it does.

A caveat kept in view: the ±2.43%-on-0.40M-cells datapoint comes from a solver with adaptive grid refinement and quasi-static equilibrium. interFoam with a static snappyHexMesh has neither and will need more cells for the same accuracy. The 2.0–2.5M figure already carries that de-rating; it is not the 0.40M figure transplanted.

Why "within 10% of Ct" is not a gate

Total resistance at these Froude numbers is dominated by friction, which any RANS code gets approximately right because it is essentially reproducing the ITTC-57 line. The quantity this case exists to compute — wave-making — is the small remainder.

Fr = 0.26, Lpp = 7.2786 m, U = 2.196 m/s, fresh water nu ~ 1.1386e-6
  Re   = 1.4046e7
  Cf   = 0.075 / (log10(Re) - 2)^2 = 2.831e-3          (ITTC-57)
  Ct   = 3.71e-3                                        (EFD)
  Cr   = Ct - Cf = 0.879e-3        <-- 23.7% of Ct

  +/-10% on Ct  =  +/-0.371e-3  =  +/- 42%  of Cr
  +/- 5% on Ct  =  +/-0.186e-3  =  +/- 21%  of Cr
  +/- 3% on Ct  =  +/-0.111e-3  =  +/- 13%  of Cr
At the issue's loose bound, the wave-making resistance could be wrong by 42% and the gate would still read green. A solution that computed no free-surface deformation whatsoever and returned pure friction would come in about 24% low on Ct — failing a 10% gate, but only just, and any partial wave field closes that margin. A Ct-only tolerance at 10% does not constrain the physics the issue is about.

V3Run Fr ∈ {0.227, 0.260, 0.282}. Require Ct(0.282)/Ct(0.260) ≥ 1.10 and Ct(0.260)/Ct(0.227) ≥ 1.03, both directions matching EFD (which gives 1.213 and 1.069).Falsifiability. A single-point match can be a lucky cancellation; a solution that reproduces the slope across a hump is doing wave-making. This also discharges the issue's "trend with Fr captured (humps/hollows)" criterion with a number instead of a picture.

Cross-check (not a gate): report Cw from holtrop_mennen.wave_resistance alongside Cr_CFD and Cr_EFD. Disagreement is recorded and investigated, not failed on — Holtrop-Mennen's own accuracy on a single hull is not good enough to fail a CFD result, and saying otherwise would be inventing authority it does not have.

Kelvin half-angle (issue criterion 4) stays qualitative: a rendered free-surface elevation field with the 19.47° wedge overlaid, in the verification report. It is a visual confirmation, is not asserted numerically, and is not counted as a gate.

Vacuity guards, per the pattern #1977 established: each of V1–V3 asserts that the reference value it compares against is non-null and was loaded from the committed reference file rather than defaulted; and the test module carries a known-negative control — a deliberately wrong Ct that must fail V1 and V2 — so a gate that has silently stopped comparing is detectable.

Environment provisioning

The constraint is that gpu-claw has no checkout and no numpy, and that its link flaps, so nothing may depend on an SSH session surviving. The repository's existing machinery already answers this and no new transport is proposed.

  1. Case generation happens locally, on the orchestrating box, by the Python emitter. What crosses the network is a directory of OpenFOAM dictionaries plus one gzipped STL — kilobytes to a few megabytes. numpy on the remote is never needed for the solve; interFoam is a C++ binary.
  2. Dispatch via scripts/setup/dispatch-cfd-run.py, which already SSH-probes for cores and load, refuses oversubscription, sources the pinned v2312 etc/bashrc, and exports CFD_DISPATCH_RANKS. Ranks are pinned to 8 to match the tutorial's hierarchical (2 2 2) decomposition.
  3. The solve is detached. The remote command is wrapped in setsid nohup with output to a log under the external work root, so the run owns no terminal and a dropped link cannot kill it. Progress is polled by short, idempotent, re-connectable SSH calls that tail the log and the forces output — never a held session. This is the one piece the existing dispatch script does not do today (it runs the remote command in the foreground of the SSH channel); adding the detach wrapper is in scope for Stage 1 and is the only change to shared tooling this plan makes.
  4. Heavy output never returns. Field time directories, processor*/ and VTK stay under the external work root per #1565. What comes back is the forces time history, the convergence log tail, a decimated free-surface slice for the figure, and the JSON manifest — with host paths redacted per the result policy.
  5. Committed evidence lands as docs/api/cfd/kcs-calm-water-resistance-verification.html plus a JSON manifest, matching the nine reports already there.

Because the link is known to flap, Stage 1's exit criterion includes surviving a deliberate disconnect: drop the SSH session mid-solve and confirm from a fresh connection that the run is still advancing.

Purpose: prove the toolchain end-to-end, measure real cell count and wall-clock, and validate the detached-run wrapper against a deliberate mid-solve disconnect. Exit criteria: checkMesh reports Mesh OK with zero failed checks; the forces history is flat over the last 500 LTS iterations; measured wall-clock recorded. This stage may invalidate the cost estimate, and the schedule is expected to change if it does.
  3. Stage 2 — emitter, RED. Write ship_resistance.py to emit a byte-comparable equivalent of the Stage-1 case from ShipResistanceConfig. Tests assert the emitted dictionaries against the tutorial's, so "did the port drop something" is a test failure rather than a divergent solve three days later.
  4. Stage 3 — Wigley smoke. Re-target the emitter at the shipped wigley.stl.gz (the L/B=10 one). Small, fast, exercises re-parameterisation. No validation claim is made from it.
  5. Stage 4 — KCS geometry and mesh. Obtain KCS_hull_SVA.zip, tessellate IGES/STP to a watertight STL, scale to 1/31.6, verify against published particulars (Lwl, B, T, ∇, Sw, Cb) before meshing. Mesh, then checkMesh to the strict verdict rule. This is the stage most likely to slip — see Risks.
  6. Stage 5 — solve and gate. Three Froude numbers. Extract Ct and Cr; evaluate V1, V2, V3; compute the Holtrop-Mennen Cw cross-check. Mesh convergence on at least two refinement levels at Fr = 0.26, since a gate passed on one mesh is not evidence of a converged solution.
  7. Stage 6 — evidence and closeout. Verification HTML + JSON manifest into docs/api/cfd/, host paths redacted. Record the G5 decision. Comment on #1173 and on #1682 with what Stage 0 delivered.

TDD test list

  • test_wigley_offsets_matches_analytic — the generator reproduces y = (B/2)(1−(2x/L)²)(1−(z/T)²) at sampled points, and the closed-form wetted surface and displacement agree with numerical integration of the generated offsets.
  • test_emitted_case_matches_dtc_tutorial — for the DTC configuration, every emitted dictionary is equivalent to the shipped tutorial's, normalising whitespace and comments. The tutorial path is read from $FOAM_TUTORIALS; the test skips loudly with a reason if unset, and asserts it did not silently pass.
  • test_control_dict_uses_lts — ddtSchemes is localEuler and maxAlphaCo is present. A regression to a transient scheme is a silent order-of-magnitude cost bomb, so it gets its own assertion.
  • test_forces_fo_on_hull_patch — a forces entry exists, names the hull patch, and uses the interFoam density field (rho rho) rather than a constant rhoInf, per the note at maccamy_fuchs.py.
  • test_parse_hull_force_roundtrip — against a committed sample of real forces output, including the half-domain doubling and the pressure/viscous split.
  • test_ct_from_force_is_dimensionally_correct — Ct = R/(½ρSU²) reproduces the EFD row from its own tabulated force, S and U. This is the check that catches a factor-of-two from the symmetry plane.
  • test_residuary_uses_ittc57 — Cr = Ct − Cf with Cf from the existing naval_architecture.resistance.ittc_1957_cf, at model Reynolds number in fresh water.
  • test_holtrop_fixture_is_enforced (Stage 0) — the fixture is loaded, every use_as_test row is consumed, and each is asserted within its own declared tolerance. Asserts the row list is non-empty and fully consumed, so a stale or empty fixture cannot pass.
  • test_v1_ct_within_5pct, test_v2_cr_within_25pct, test_v3_froude_trend — solve-asserts, gated on solver_capable, reading the committed run manifest.
  • test_gate_rejects_known_bad_value — the known-negative control: a fabricated Ct 25% low must fail V1 and V2. Without this, a gate whose reference silently became None reads green.

Acceptance criteria

  1. A KCS calm-water resistance case is emitted from ShipResistanceConfig and runs to convergence via the existing runner on the pinned v2312 toolchain — solve-asserts PASS on a solver-capable host, not skip. (#1192's fourth criterion, adopted here because a skipped gate is the failure mode this repository keeps rediscovering.)
  2. checkMesh on the KCS mesh reports Mesh OK and zero failed checks — verified from output text, not exit code.
  3. V1: Ct within 5% of the pinned KCS EFD value at Fr = 0.26.
  4. V2: Cr within 25% of Cr_EFD at Fr = 0.26.
  5. V3: the Ct trend across Fr ∈ {0.227, 0.260, 0.282} reproduces both EFD ratios within tolerance.
  6. Mesh convergence demonstrated across at least two refinement levels at Fr = 0.26, with V1 satisfied on the finer.
  7. The known-negative control fails the gate, proving the gate is live.
  8. Stage 0's Holtrop-Mennen fixture test is enforced and green, and the Holtrop Cw cross-check is reported alongside Cr in the verification artifact.
  9. Free-surface elevation rendered with the Kelvin wedge overlaid, in the verification HTML.
  10. Hull source, model scale, Froude number, Reynolds number, water properties, OpenFOAM build and citation recorded in the case provenance and the JSON manifest.
  11. The G5 decision — reuse, no new CaseType — is documented in the module docstring with its reasoning.
  12. scripts/enforcement/check-no-abs-paths.sh --added origin/main and the workspace legal sanity scan both pass; no host path appears in any committed CSV, JSON, log tail or report.

Risks and fail-closed responses

riskresponse
KCS geometry acquisition fails or the tessellation is not watertight. The workshop publishes IGES/STP, not STL. No IGES import path exists in the repository — hull_library/exporter.py writes WAMIT GDF, OrcaWave and SVG only, and the BEM panel meshes it produces are quad-based and orders of magnitude too coarse for snappyHexMesh. This is the top schedule risk.Stage 4 is deliberately late, after the harness is proven, so a slip here costs geometry time and not the whole plan. Verification is against published particulars before meshing, so a bad tessellation is caught in minutes rather than after a 12-hour solve. Fallback if it proves intractable: deliver against DTC, and accept the weaker (paywalled) reference with the gate restated on V2 and V3 only — explicitly a degraded outcome, recorded as such, not quietly substituted.
The cost estimate is wrong and KCS does not finish.Stage 1 measures it on the real box before any KCS work starts. If the measurement blows out, the response is to reduce scope to one Froude number plus the trend check at coarser resolution — not to loosen the tolerance, which would convert a real gate into a decorative one.
The fixed-body assumption biases Ct. The reference EFD is for a model free to sink and trim; the reference CFD study solved for dynamic equilibrium in heave and pitch. A fixed body at Fr 0.26 typically under-predicts resistance.Named here rather than discovered at Stage 5. The issue specifies a fixed body and this plan honours that, but the bias is real and directional. Stage 5 reports the fixed-body result against the EFD sinkage and trim so the discrepancy is quantified rather than absorbed. If V1 fails on this bias alone, the honest resolution is a follow-on issue for free sinkage and trim — not widening the tolerance until the number fits.
The gate passes for the wrong reason — compensating errors between an over-predicted friction and an under-predicted wave field.This is what V2 and V3 are for, and it is why V1 alone was rejected. The reference value is second-hand. The verified Ct table reproduces the workshop EFD but is not the workshop's own publication, and published KCS Ct values differ between model scales because Ct carries Reynolds-dependent friction.Stage 0 pins the primary source before any gate is written, and the fixture records scale and Reynolds number per row so a value can never be compared across scales by accident. A KCS Ct quoted without its model scale is not a reference.
gpu-claw's WireGuard link drops mid-run.Detached setsid nohup execution; progress polled by short reconnectable calls; Stage 1 proves survival against a deliberate disconnect before any long run is started.
Scope creep into #1192.Out of bounds. This plan is shaped by #1192's lesson but fixes neither the flat plate nor the cylinder. If the port reveals a generic fix that would also unblock them, it is filed as a comment on #1192, not absorbed here.

Out of scope

  • Free sinkage and trim, self-propulsion, propeller and rudder — separate issues; the bias from omitting them is quantified, not fixed.
  • Full-scale extrapolation to delivered power (ITTC-78). The deliverable stops at the model-scale coefficient.
  • #1192's flat-plate and cylinder cases, and the broader question of whether OpenFOAMCaseBuilder should be repaired or retired.
  • A general IGES/STEP import capability. Stage 4 needs one KCS hull tessellated once; building a reusable CAD import pipeline is #1161 Phase 3 work.
  • Added resistance in waves and seakeeping — #470 and the parametric hull work; note that hydrodynamics/parametric_hull_analysis/forward_speed.py is seakeeping (DNV-RP-C205 §7.4 encounter-frequency corrections) and is not a foundation for any of this.

Adversarial review

Tier T2 proposed — multi-file, new solver capability, remote execution, but a single well-bounded domain. Reviewers should be pointed at these specific claims, which are the ones most likely to be wrong:

  • The cost estimate. It rests on a 2.5e-5 core-second per cell-iteration constant back-derived from a narrative markdown file whose mesh size is not recorded — the 0.7M cell figure is an assumption, not a measurement. If it is off by 3×, KCS at three Froude numbers stops fitting in a working week. Stage 1 is placed where it is because of this, but a reviewer should challenge whether Stage 1 is early enough.
  • The V2 threshold. 25% on Cr was chosen to be roughly equivalent to 6% on Ct; it is a judgement, not a derivation, and no published uncertainty band for the EFD Cr was located to anchor it.
  • The claim that Wigley forfeits the Holtrop-Mennen cross-check. This is argued from the method's regression basis, not from a citation stating an exclusion. If a reviewer can show Holtrop-Mennen is defensible on a Wigley form, the hull recommendation weakens considerably.
  • The Stage 0 split. Carving half a day of #1682's scope into this plan may be the wrong call organisationally even if it is right technically. The alternative — Stage 0 as a hard blocker owned entirely by #1682 — is stated in the sequencing section and a reviewer may prefer it.
  • The fixed-body bias. If it is large enough to consume the whole 5% V1 budget on its own, then V1 as written is not achievable and the plan should say so before approval rather than discover it at Stage 5.

Reviewers should verify claims against the repository and the host rather than against this document; several figures here were re-derived after an initial reading proved wrong, and the premise correction at the top of this plan came from re-running a command that had been reported as authoritative.
