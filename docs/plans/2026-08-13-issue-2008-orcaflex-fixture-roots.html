#2008 implementation plan: declared fixture roots must exist

Issue #2008 · branch plan/2008-orcaflex-fixture-roots · base 2a6b521e · drafted 2026-08-13 · status: awaiting user approval

Goal and authorization boundary

A test module that declares a filesystem root will find that root, or the suite will go red. Today four modules declare roots under a docs/modules/ tree that has never existed in this repository's history, and every one of them degrades to something that reads as success.

  • G1 — Every data root declared by a test module under tests/ will resolve to a path that exists, or the module will not declare it.
  • G2 — No test will report skipped because a declared data root is absent. Skips for an absent capability (no OrcaFlex licence, no OrcFxAPI) remain legitimate and are explicitly preserved.
  • G3 — A guard test will fail when a test module declares a root that does not resolve, so the next tree move cannot silently reopen this hole. The guard will key on the property, not on the literal string docs/modules.
  • G4 — The real, reproducible coverage of the format-converter suite will be recorded on #280 and #518, whose acceptance evidence this defect invalidates.

Boundary. This plan repairs path resolution and skip semantics. It will not modify converter behaviour in src/, will not author new model data, and will not attempt to make any test pass that fails for a genuine reason once its data is found. Any test that newly surfaces red will be recorded as a pre-existing finding with its own follow-on issue, never repaired inside this branch. It will not set status:plan-approved.

Chosen mechanism for the guard

Issue acceptance criterion 4 asks for "a guard that fails if any tracked test file references docs/modules/". That guard must not be built as specified.

A string-matching guard would be red against correct code on the day it lands. test_model_generator.py and test_template_generator.py contain the literal docs/modules in docstrings that document the fix for this defect class. A grep-based guard fails on both, and the only ways to make it green are to delete accurate documentation or to add per-file exemptions — which are backdoors. It is also too narrow in the dimension that matters: it pins one dead string, so the next layout change (docs/domains/ to anything else) reopens the hole with a guard still shining green.

The guard will assert the property instead: every filesystem root a test module declares must resolve. It will be a contract test under tests/contracts/, matching the precedent set by test_collection_visibility.py (#1977/#1983), and it will work by AST inspection, not text search. Parsing with ast makes docstrings and comments invisible by construction — the false-positive problem disappears rather than being exempted away.

# tests/contracts/test_declared_data_roots.py  (sketch, not final)
#
# For every module under tests/, walk module-level Assign nodes whose value is a
# chain of BinOp(Div) over an anchor expression (Path(__file__).parents[N],
# PROJECT_ROOT, DIGITALMODEL_ROOT, ...) with all-literal segments.  Resolve the
# segments against the repo root.  Assert the path exists.
#
# Docstrings are not Assign nodes.  Comments are not in the AST at all.

Two complementary properties, both needed — the first stops a root being declared dead, the second stops a live root's absence being swallowed at runtime:

  • P1 (static). No module-level path constant in a test module resolves to a nonexistent path.
  • P2 (dynamic). No test in the format-converter suite reports skipped with a reason indicating missing data. Implemented by changing the three conftest fixtures from pytest.skip to a hard failure, and asserting the property in the contract test via a -rs parse or a pytest.ini-level check.

Per the test_collection_visibility.py precedent, the guard carries explicit vacuity defences, because a scanner that finds nothing reports a confident green:

  • The set of discovered declared roots is asserted non-empty, with a floor well below the current population.
  • A known-positive control: the resolver is run against a synthesised dead path and asserted to report it, proving the checker is live rather than returning "fine" for everything.
  • A known-negative control: a path known to exist is asserted to pass, proving the resolver is not reporting everything as broken.
  • Any exemption list is asserted fully consumed, so a stale exemption cannot mask a new offender.
Scope note the issue does not raise. The same component search finds docs/modules path construction in eleven files under scripts/ and one YAML under docs/domains/orcawave/. A guard scoped to tests/ — as AC 4 specifies — leaves all twelve dead. They are out of scope here (they are not tests and break no coverage claim), but the guard will be written so its root set is a parameter rather than a hardcoded tests/, and a follow-on will be filed to extend it.

  1. Stage 1 — guard test, RED. Author tests/contracts/test_declared_data_roots.py and commit it failing, naming the four dead roots. Open the pull request at this stage and leave it red: per the #1977 finding, the domain gate triggers on pull_request, so a push to the branch alone produces no CI evidence that the guard was ever able to fail.

  4. Stage 4 — record and file. Post the before/after evidence on #2008; post the correction on #280; file the follow-ons (RAO module, input_file data, scripts/ guard extension).

Stages 1–3 are the fix. Stage 4 exists so the evidence correction is not buried inside a code commit.

TDD test list

Every assertion is on a property. No test pins 116, 35, or 81 — the first two are already stale in the issue, and the third changes the moment a converter test is added.

  • test_every_declared_data_root_resolves — P1. Fails at Stage 1 naming the four dead roots; passes from Stage 2. Carries the four vacuity defences above.
  • test_resolver_reports_a_synthesised_dead_root — the known-positive control, asserted before the main assertion in the same module.
  • test_resolver_accepts_a_known_live_root — the known-negative control.
  • test_no_format_converter_test_skips_for_missing_data — P2. Runs the suite and asserts that no skip reason indicates absent data, while allowing capability skips. Must assert the run collected a non-trivial number of tests, or an empty run satisfies it vacuously.
  • test_capability_skips_are_still_permitted — the counterweight. Asserts a licence-gated skip is not flagged, so a later tightening cannot force OrcFxAPI-dependent tests into red on unlicensed hosts. Without this, the obvious "no skips at all" over-correction looks correct and breaks every Linux run.
  • test_a01_round_trip_executes — a named, property-shaped assertion that the real-model round-trip test runs rather than skips. This is the single test whose absence #518 cares about; it deserves a guard that names it, not a bulk count.

Acceptance criteria

  1. No test module under tests/ declares a data root that fails to resolve. Stated as a property, not as "the four known ones are fixed" — the guard must reject a fifth introduced tomorrow.
  2. No test skips because a declared data root is absent, in the format-converter suite or the three other affected modules. Capability skips (OrcFxAPI) are unaffected and are asserted to remain permitted.
  3. The guard is demonstrably RED at the Stage 1 commit and GREEN at Stage 2, provable from CI history on the pull request.
  4. A node-ID diff across Stages 1–3 shows zero tests removed from the format-converter suite, and every previously-skipped node ID now reports a real outcome. Any that report failure are filed as pre-existing findings before merge and are not repaired in this branch.
  5. test_round_trip.py::test_roundtrip_real_a01 executes and reports a real outcome.
  6. The solver-marked and unsupported-marked tests each carry a written reason, and every unsupported mark links a filed issue. No test is left marked with a bare reason string.
  7. A comment on #280 records that its "102 tests passing" evidence was measured on a lineage whose data path does not exist on origin/main, states the reproducible figure before and after, and links this plan. status:blocked is left in place.
  8. A comment on #518 records that its end-to-end criterion was unassessable and now is assessable — explicitly not that it is satisfied.
  9. Both gate lanes green: tests/solvers/orcaflex/ and tests/contracts/.

Adversarial review summary

Reviewers should attack, at minimum:

  • The AST-scanner design. What declaration shape defeats it? Is the "unanalysable" bucket honest, or does it become a silent exemption channel?
  • The G2 boundary between absent root and absent capability. Is it decidable from the information available at fixture time, or does it require the author to classify correctly — in which case it will be got wrong.
  • The claim that 116/116 pass under the repoint. It was measured once, locally, on a patched-then-reverted working tree. Re-measure independently.
  • The provenance argument. Does git log origin/main -- docs/modules returning zero commits actually support the conclusion drawn, given the 2c185d2d history rewrite?
  • Whether the two "false positive" modules are truly prose-only, or whether a reviewer can find a live path construction in them that this analysis missed.
  • Whether marking the input_file tests unsupported is the right call versus deleting them, given that a marked test with no data is itself a form of standing green.
