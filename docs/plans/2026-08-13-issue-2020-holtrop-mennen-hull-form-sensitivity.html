Goal and authorization boundary

Holtrop-Mennen will be pinned to an oracle that lives outside this repository, and the pin will be enforced by a test that runs. Today the module's only numeric checks are bands wide enough to admit almost any answer, and its declared test vectors are un-sourced numbers that no test reads.

  • G1 — The module's output will be validated against a published Holtrop-Mennen worked example with printed intermediate values, so that each coefficient function has its own oracle rather than only the total having one.
  • G2 — Which published formulation this module implements will be established first (Finding 4), and every coefficient that departs from it will then be corrected, each behind a test that fails first and that actually exercises the corrected path.
  • G3 — tests/fixtures/test_vectors/naval_architecture/holtrop_mennen.yaml will be loaded by a parametrized test that asserts every row marked use_as_test: true, so that flag stops being decorative.
  • G4 — Every expected value in that fixture will carry a citation naming where it came from, or it will not remain in the fixture.
  • G5 — A hull-form sensitivity test will assert the separation of CT across a declared hull set, and will assert ordering only where ordering has been derived from the published equations across that set's whole range, so a future regression that flattens hull dependence fails loudly even if every band still passes. (Narrowed at revision 3 — round 2 NEW-2. An earlier draft required “direction and ordering” unconditionally, which contradicted AC 4 and the experimental design, both of which permit separation without ordering. Finding 1 is the reason ordering cannot be assumed: CT is a sum of terms that move in opposite directions with fullness. The goal now states the weaker requirement the rest of the plan can actually meet.)
  • G6 — The published artifact docs/api/structural/ship-resistance-explorer.html, which is generated from this engine, will be regenerated so the public surface and the engine agree.

Boundary. This plan will change the resistance engine, its tests, its fixture and the artifact generated from it. It will not touch the CFD work in #1173, will not extend the method beyond the Fn < 0.4 regime it implements today, and will not add propulsion or wake-fraction estimation. It will not self-apply status:plan-approved.

Finding 1 — the collapse hypothesis is refuted. Every term discriminates. S differs by a factor of 3.95, iE by 5.15, c1 by 3.49, 1+k1 by 1.16. No term is form-insensitive. The near-identity in CT is a three-way cancellation at these two specific operating points: moving from the Series 60 to the tanker, CF(1+k1) rises 8.8% while CW falls 6.4% and CA falls 26.2%, and the component weights make the sum agree to 4 parts in 105. The issue's candidate mechanism — "RT and S scale together so the ratio cancels" — is confirmed as an observation (RT ratio 3.9515 against S ratio 3.9514) but refuted as a cause: that equality is the restatement of CT equality, not its explanation. The two other candidate mechanisms are also refuted: no form-dependent term is computed-but-unapplied (all six components are applied, and all six discriminate), and there is no non-dimensionalisation error (CF was re-derived from ITTC-1957 independently at both Reynolds numbers and matches). The m1 near-equality is a genuine second coincidence, unrelated to the first, and it does not propagate because c1 differs by 3.49×.

The argument in its strongest form removes the form-factor regression — but not every regression

Round 1 correctly observed that a floor computed from the module's own form_factor_k1 is not source-independent: an understated k1 understates the floor, so the guard weakens exactly when the module is wrong. That objection is sound in general, and it is answered here by removing the dependence rather than by defending it.

The claim is narrowed at revision 3 — round 2 NEW-4, in which the reviewer corrected their own round-1 wording rather than the plan's. Round 1 wrote that the substitution gives a floor “using no Holtrop-Mennen regression at all”. That is overstated, and revision 2 repeated it. Substituting (1+k1) = 1 removes the form-factor regression; it does not remove CA, which is itself a Holtrop-Mennen regression evaluated by this module and which carries defect C-6. The precise statement, in three parts:
  • Unconditionally source-independent: CF (ITTC-1957, a closed formula) and the bound (1+k1) ≥ 1 (a physical definition). Neither involves any regression from either paper.
  • Where C-6 is dormant — T/L ≥ 0.04, which makes c4 = 0.04 and therefore (0.04 − c4) = 0 — the implemented and corrected correlation_allowance are identical expressions, so the floor is independent of every defect in the inventory. The tanker conclusion sits here and is unaffected: ABT = 0 and T/L = 12.0/205.0 = 0.0585 > 0.04 both hold, so C-6's term is identically zero for that row.
  • Where C-6 is active — T/L < 0.04 and ABT > 0 — the implemented CA omits a factor c2 ∈ (0, 1] from a non-negative term, so the implemented CA is an upper bound on the corrected CA, and the implemented floor is an upper bound on the corrected floor. The guard's error there can only produce a false rejection, never a false acceptance. It remains safe to run and unsafe to certify with, so a row failing the guard under active C-6 will be investigated rather than removed.
Dropping CA altogether does not rescue the argument, and the plan will not claim it does: CT ≥ CF gives 1.477744e-03 for the tanker, which is below the 1.75e-03 fixture value and rejects nothing. CA is load-bearing for Finding 2, so the narrowing above is the strongest honest form, not a stylistic softening.

A form factor is (1+k1) ≥ 1 by physical definition — viscous resistance cannot fall below flat-plate friction on the same wetted surface. Substituting the physical minimum (1+k1) = 1 gives a floor that references no Holtrop-Mennen regression whatsoever:

The tanker's ct_approx = 0.00175 cannot be produced by Holtrop-Mennen for that hull at that speed, by any correction to this code. It sits 24% below the method's own computed floor of 2.2966e-3, and — the form that survives every objection — 4.4% below the floor obtained at the physically minimal form factor of exactly 1.0, which no coefficient defect can lower. Reaching 0.00175 requires either CW < 0 or (1+k1) < 0.9457. The number is not a tolerance miss. It is outside the method's range.
The negative-CA escape is provably closed, not merely unobserved. The third term of correlation_allowance is +0.003*sqrt(L/7.5)*Cb**4*(0.04 - c4) with c4 = min(T/L, 0.04), so (0.04 - c4) ≥ 0 for every input, always. The term can never subtract. The floor therefore does not depend on that term vanishing for these two hulls, and the remaining two terms give CA = 0.006(L+100)−0.16 − 0.00205, which crosses zero only at L = 722 m. Both escapes an earlier draft invited reviewers to hunt are closed by inspection; the hunt is not re-issued.

Solving for the Reynolds number at which the module's own CW and (1+k1) would give CT = 0.00385 with CA = 0 — the model-scale convention, where no correlation allowance is applied — yields:

6.05 m is an unremarkable towing-tank model length for a 122 m ship. The Series 60 value is therefore consistent with a model-scale CT recorded against a full-scale input row. The same inversion applied to the tanker requires CF = 7.62e-04, which ITTC-1957 reaches only beyond Rn ~ 1012; there is no physical scale, model or full, at which 0.00175 is that hull's CT.

Read together, Findings 2 and 3 say the fixture is not a usable oracle. One row is plausibly a model-scale number mislabelled as full-scale; the other is outside the method's range at any scale. The fixture's provenance block names the two Holtrop papers as source_type: journal_paper, but neither paper tabulates these two hulls, and the repository contains no derivation for either number. The fixture is best explained as plausible-looking values authored alongside the module rather than extracted from a source — which is exactly the failure mode use_as_test: true was supposed to prevent, and could not, because nothing read the flag.

This row is the strongest independent evidence for the method-version question in Finding 4. The band [1.18, 1.25] was authored by someone in this repository, for a hull whose parameters they also authored, and the module misses it in the same direction both as shipped and after C-1. The most economical explanation is that the band was written against a different formulation of (1+k1) than the code implements — which is precisely the 1982-versus-1984 question Stage 1 will settle. The row is therefore treated as evidence about the version, not merely as a wrong number to be re-sourced, and its disposition is settled at Stage 1d, immediately after Stage 1a fixes the version and before any test is authored. Two further structural problems with this row, both blocking AC 2

  • The row is marked use_as_test: true and cannot pass. Its band is missed as shipped (1.12014) and after C-1 (1.13616). An earlier draft discussed this contradiction in prose while no inventory row and no acceptance criterion owned it, so the plan could have reached implementation with AC 2 and AC 7 jointly unsatisfiable. It is now owned explicitly by AC 2(d) and appears as row F-1 in the fixture disposition table below.
  • The row carries no ct_approx key at all — only k1_plus_1_min and k1_plus_1_max. An earlier draft specified test_fixture_vectors as asserting ct_approx for every enabled row, which this row cannot supply. The test as specified could not consume it, so AC 2 was unsatisfiable on a second, independent ground. The fix is not to invent a ct_approx for it: it is that the fixture contract becomes key-driven — each expected-value key maps to a named assertion, a row is consumed when every key it carries has been asserted, and rows legitimately carry different key sets. That mapping is specified in the expected-key-to-assertion mapping and enforced by AC 2(c).

What Stage 1 will establish, and record on the issue before any coefficient is touched:

  • Which formulation each coefficient function in this module implements, function by function, cited to a specific equation number in a specific paper.
  • Which formulation the selected worked example assumes, cited the same way.
  • Whether those two are the same. If they differ, whether the module is retargeted to one version or the oracle is replaced — a decision that will be recorded on the issue with its reasoning, not made silently inside an implementation commit.
  • What the module docstring should say once the answer is known, since it presently asserts an answer the plan cannot yet support.

C-9 bears directly on the floor guard. It is the concrete instance of the objection answered in Finding 2: a module-computed floor inherits whatever form_factor_k1 returns, including values that are physically impossible. This is a second reason the floor test is specified against the physical bound (1+k1) ≥ 1 rather than against the module's own return value, and a reason the guard is worth adding even though nothing shipped today reaches it.

Correcting every active coefficient defect does not close the gap to the fixture. Measured end to end: with C-1 and C-2 both fixed, series60 moves from −31.5% to −30.9% and the tanker from +50.6% to +51.8%. The two effects are worth roughly 1–3% of CT, not 30–50%. Anyone who plans a fix by chasing the percentage errors will keep finding defects that do not explain them. This is the plan's central reason for putting the oracle before the fix.

The mapping is proved by execution, not by declaration

Round 2 B3, second part, accepted. test_no_unmapped_expected_keys as specified proves only that a key's name appears in a hand-maintained mapping table. The mapping therefore stops being a declaration and becomes a record of what actually ran:

  • Each per-key assertion records itself. Every per-key test writes the pair (row_id, key) into a session-scoped ledger at the point where it asserts, not at collection time and not from a decorator argument that could disagree with the body. A test that is skipped, that returns early, or that never reaches its assertion records nothing.
  • A terminal check compares ledgers, not tables. After the session, the set of (row_id, key) pairs in the ledger must equal the set of (row_id, key) pairs the fixture declares across its enabled rows. The symmetric difference is reported, so an unasserted expected value and a phantom assertion are distinguishable.
  • The hand-maintained mapping survives only as documentation. It is retained in this plan and in the test module's docstring because a reader needs it, but no criterion depends on it. AC 2(c) is rewritten against the ledger. If the table and the ledger disagree, the ledger is right and the table is stale.
  • The known defeat is written down so it is not reintroduced. A ledger populated from a decorator or a module-level registry rather than from the assertion site would restore the original vacuity, because the registration would survive the assertion being deleted. Registration must be lexically inside the assertion path.

This is the same correction as round 1's count-to-set-equality fix, applied one level higher: the earlier proof asked “is it declared?” where it needed to ask “did it run?”.

Why the consumption proof changes

Count equality does not prove set equality. An earlier draft proved consumption by asserting that the collected parameter count equalled the number of use_as_test: true rows. A loader that duplicates one row and omits another preserves the count exactly, and the proof passes while a row goes unasserted — the same class of vacuity the fixture guards were written to prevent, one level up. Round 1 is correct and the proof is replaced.

The replacement, enforced by AC 2:

  • Unique row IDs. A duplicate id in the fixture fails at load, before any parametrization. Uniqueness is asserted, not assumed from YAML structure.
  • Set equality, not count equality. The set of IDs marked use_as_test: true in the file and the set of IDs actually collected by the parametrized tests must be equal as sets. The assertion reports the symmetric difference on failure, so a missing row and a spurious row are distinguishable rather than cancelling.
  • Key coverage per row. For each consumed row, the set of expected-value keys it carries must equal the set of keys asserted for it under the mapping above. A row carrying a key nobody asserts fails; a test claiming a key the row lacks fails.
  • Non-vacuity, retained. The YAML resolved and parsed; the collected count is non-zero; every consumed row carries a source. These remain necessary — they are simply no longer treated as sufficient.

Device 3 — entry gates, no decisions in GREEN, and a loop-back

Ordering stages does not gate them; revision 2's stages were a narrative that an implementer could label complete at will. Three rules make them binding:

  • Entry gates. A stage may not begin until every entry condition is recorded CLOSED, with evidence, in a comment on #2020. Stage 2 may not begin until: the version is determined and recorded (AC 10); an admissible worked example is in hand and its printed intermediates enumerated (AC 1); every freeze-register parameter has a value on the record; F-1, F-2 and F-3 are dispositioned; and the whole inventory is re-confirmed against the primary paper, including any row F-1 adds. Stage 3 may not begin until every test in the TDD list is committed, pushed, and failing, with a per-defect RED evidence table showing that each activating condition actually produced a failure. Stage 4 may not begin until the verification scope is green.
  • No decisions in GREEN. Stage 3 may correct code and nothing else. It may not choose a tolerance, adjust a threshold, re-scope an activating condition, disposition a fixture row, or re-source a value. If it needs to do any of those, it has found something Stage 1 missed, and it stops.
  • Loop-back. Anything discovered late returns to the stage that owns it, and the stages after that one are re-entered through their gates. A new defect found at Stage 3 goes back to Stage 1 for its equation and its frozen expected value, then to Stage 2 for its failing test, before Stage 3 resumes. A defect is never corrected in the same stage that discovered it — that is the concrete form of “fails first”, and its absence is what round 2 identified in B3's outcome (a).
What this costs, stated honestly. Stage 1 becomes large and the plan cannot start until an admissible source exists. That is the intended trade: this issue exists because numbers entered a fixture without provenance and nothing downstream could tell. A plan that lets Stage 3 decide anything reproduces that at the level of the plan. The cost also means the replan gate is more likely to fire than under revision 2, and that is correct behaviour, not a defect.

Tolerance rules, frozen at Stage 1c

The two rules are unchanged from revision 2 in substance; only their timing moves, which is what round 2 finding 6 required. (Round 1 is correct that the method's stated predictive accuracy is the wrong figure for a worked-example pin: it describes agreement between the method and physical towing-tank data, not numerical reproduction of its equations, and a band that wide hides a several-percent coefficient error comfortably.)

  • Reproduction rows (F-4 and any other worked-example row) take a tolerance derived from the printed precision of the published value and the rounding propagated through the equations that produce it. If the paper prints 1+k1 to five figures, the tolerance is set by that last figure and by the precision of the inputs feeding it — not by anything about how well the method predicts reality. Where propagation is not analytically obvious, it will be bounded by perturbing each printed input across its last-digit interval and taking the resulting spread. A reproduction row that needs a loose tolerance to pass is reporting a defect, and will be treated as one.
  • Empirical rows (any row whose expected value comes from measured data rather than from a printed calculation) may use the method's stated uncertainty, because for those rows that is the relevant figure. Each such row will state which rule it uses, in the fixture, as a required key.
  • Both are computable from the source alone, which is the point round 2 forced. Neither takes any module output as an input, so neither had any reason to wait until the corrections were visible, and after Stage 1c neither may be changed without a loop-back.
  • The known degeneracy is recorded rather than assumed away. Round 2's predecessor asked whether the perturbation rule degenerates when the paper prints inputs to fewer figures than the module consumes, making the admissible interval wide enough to swallow the defects being hunted. If Stage 1c finds an intermediate whose bounded interval exceeds the effect size of any inventory defect that feeds it, that intermediate is recorded as non-discriminating and does not count toward AC 1; the equation test for its coefficient carries the weight instead. This is measured at Stage 1c per intermediate, not asserted here.

C-9's required behaviour: form_factor_k1 raises

Round 2 NEW-5, accepted. Revision 2 specified a test that accepts form_factor_k1 either raising or being bounded. Round 2 is right that these are materially different APIs and that a test accepting either drives no implementation — it would pass against a silent clamp and against an exception, so it constrains nothing an implementer might choose.

The decision: it raises. Two reasons, in order of weight:

  • Clamping manufactures a plausible wrong number, which is this issue's own failure mode. A clamp to 1.0 returns a value that flows into CF(1+k1), into CT, into the workflow layer and onto the published page, carrying no signal that the regression was evaluated outside its domain. The reader downstream sees a number that looks like every other number. That is precisely how ct_approx = 0.00175 came to sit in a fixture for months: nothing distinguished an unsupported value from a supported one. A guard that silently substitutes a defensible-looking number is a smaller version of the same defect.
  • It matches the sibling guard the same branch adds. C-8 rejects out-of-range Froude numbers by raising rather than by extrapolating silently. Two domain guards on one module resolving the same situation two different ways would be an inconsistency introduced by this plan, and a later reader would have to discover which does which.

The raise carries the offending inputs and the bound violated, so the exception is diagnostic rather than merely obstructive. A clamp is not offered as a configurable alternative, since a flag that restores the silent path restores the defect for anyone who sets it. If a caller legitimately needs to evaluate outside the envelope, that is the follow-on about documented validity envelopes already in the out-of-scope list, and it is a different design conversation.

The test is retained, unchanged in what it asserts, and reclassified from a red test to a regression guard with a mutation-based fail-first proof:

  • Its fail-first evidence is a mutation.   • Its docstring states its own status — that it passed on the engine as first written, that it exists to catch a regression this issue makes plausible rather than one it found, and that the reported near-identity was a fixed-speed coincidence. Acceptance criteria

  1. The module reproduces a published worked example end to end, and each intermediate that example actually prints, each within a tolerance set by the reproduction rule and frozen at Stage 1c, before any corrected output exists — printed precision and propagated rounding, never the method's empirical accuracy. The set of printed intermediates is enumerated from the source at Stage 1 and recorded on the issue; intermediates the source omits are covered by independent equation tests, labelled as the weaker oracle they are. The source is cited in the fixture and in the test.
  2. The fixture's consumption is proven by set equality, not by a count. Specifically, all four of:
    1. Row IDs are unique, asserted at load.
    2. The set of IDs marked use_as_test: true equals the set of IDs collected by the parametrized tests. A row added and enabled without a corresponding assertion fails; so does a collected ID with no enabled row behind it.
    3. Proved by execution, not by declaration. (Rewritten at revision 3 — round 2 B3.) The set of (row_id, key) pairs recorded in the execution ledger at assertion time equals the set the fixture declares across its enabled rows. No expected value goes unasserted, and no test claims a key its row lacks. The hand-maintained key mapping is documentation only and no criterion depends on it; where the two disagree the ledger governs.
    4. No enabled row is left failing. A row that is enabled, asserted, and red does not satisfy this criterion, and neither does one quietly disabled without a stated reason.
  3. Every expected value in the fixture carries a source, an explicit scale convention, and a declaration of which tolerance rule it uses (reproduction or empirical). No un-sourced number remains.
  4.
