Issue: 2121. Lane: Codex. Client: N/A. Scope: T2, one existing canary prefix; disjoint offline preparation. Standing non-destructive lifecycle authorization will apply. A reciprocal Claude review will precede application of this amendment and native use.

Source disposition

The existing campaign plan at377be1d53 will be treated as the source of the competent owner-appointed checker prerequisite before B2. The requirement will not be attributed to a user demand for a human signature or to vendor licensing: neither basis has been established. The code will continue requiring distinct operator/checker identities. The original full-canary and qualified-reuse paths will retain their gates.

This amendment will apply only to diagnostic capture of the existing first zero-load case. The actual SOLVERS lane identity will identify the operational executor. An actual independent Claude review-session identity, bound to the exact current code/configuration review, will identify the diagnostic software/numerical reviewer; it will not identify a competent human engineer or confer engineering authority. The frozen independent analytical reference and its provenance checks will remain mandatory and unchanged. No dummy checker, self-issued engineering signature, reconstructed derivation or automatic qualification will be permitted.

The current observer's any-mpiexec filter will be replaced by a source-bound conflict classification. The plan's recording of existing processes will not be interpreted as a blanket prohibition on unrelated CFD. All inspected processes and dispositions will remain retained; only actual ANSYS competitors and unresolved relevant processes will enter the existing preflight conflict field. Host capacity will remain a separate check.

Executable method and boundaries

  1. The production entry point will verify the current reviewed source/configuration hashes, actual provider review receipt and user-authorized diagnostic scope. The dedicated invoking process will supply ANSYS261_PRODUCT=ansys and ANS_CONSEC=YES; the entry point will refuse mismatching inherited values before preflight and again immediately before the existing launch callback. The same environment will pass to the child through the existing runner's inheritance. No machine/user environment or existing launch API will change. The environment will be bound in execution_binding, the approval digest and retained preflight. The profile will equal cylinder_canary.PROFILE: cores1,parallel=smp,timeout_seconds300. The pinned executable and frozen output identity checks will remain unchanged.
  2. The operational reservation will use the existing local queue lock path, with exclusive creation and owner-token readback. This will serialize participating local licensed routes. A live successful licence query will establish availability; it will not be labelled a global reservation or a vendor checkout. The resulting native launch will still be subject to vendor licence refusal. Lock release will require proof that no owned solver remains; uncertainty will retain the lock and evidence. No stale-lock takeover or CFD/control mutation will occur.
  3. The admitted campaign ID and resolved ledger residence will be fixed by a separately bound configuration and externally recorded config/review pins. Existing consumption, a partial claim, configuration drift, redirected storage or an unknown process disposition will refuse execution. Within those fixed pins, a new manifest, directory, process restart or substituted ID will not reset the consumed campaign allowance. The mechanism will not claim cryptographic prevention of an independently reconfigured campaign with different external pins; issuing such a replacement will be outside this diagnostic admission, rather than an automatic retry route.
  4. The unchanged run_canary API and make_execution_adapters will execute the existing first case. verify_authority will permit only the unconsumed diagnostic claim. Once the durable claim exists, the next preflight will raise an explicit diagnostic-scope-exhausted refusal before the second launch. No call-count-only or in-memory allowance will be used. The adjudicate callback will refuse if reached; it will never return a fabricated engineering proof.
  5. A valid first-case assessment followed by the planned scope stop will leave the four-case campaign INCOMPLETE with three unattempted cases, while retaining the first diagnostic record and checks. A zero-control FAIL will remain FAIL. A refusal before the durable claim will leave four cases unattempted and the allowance unconsumed. Every failure after the durable claim, including timeout, stream mismatch, partial evidence or a crash before journaling, will consume the allowance and end this admitted diagnostic attempt. No retry or new-ID re-admission will be supported by this amendment. Every retained native record will remain provisional and unqualified. The three pressure cases will remain inaccessible under the current API: future continuation will require new reviewed ledger-driven resume code, prior-prefix assessment and preserved claim handling. This amendment will not claim a working continuation.

Production interfaces and ownership limits

The immutable admission config will contain campaign_id, operational operator_id, the fixed absolute ledger_directory, scope limited to the single zero-control case, relative source-file digests and execution_binding. execution_binding will include manifest/executable digests, execution host, solver/runtime profiles, launch_environment and capture/reserve budgets. It will not include future review hashes or the future reviewer session, avoiding a config/review hash cycle. make_diagnostic_admission will receive separately pinned config/review hashes and the retained raw review bundle from the trusted SOLVERS invocation. The SHA-256 of the original bundle bytes produced by the existing review helper will be recomputed and compared with the actual reviewer's structured verdict; the bundle context/path/content/digests will not be reconstructed from a caller's file list. Every reviewed file's current raw hash and UTF-8 content will match the bundle and receipt. Config source_files will cover the internally derived loaded runtime_sources plus the production entry point; a caller-supplied narrowed source inventory will not be accepted. Loaded source-root identity and the running entry point will be checked. The raw review transport digest and actual reviewer session ID will be bound, and the entire typed approval object will be required to match exactly. These external pins and the recorded standing user instruction will remain trust boundaries, not self-authenticating JSON authority.

Process snapshot scope will be the selected possible ANSYS/MPI families and their relevant ancestors/descendants after a complete initial PID/name/path enumeration. Selection/omission counts and the selector will be retained; complete enumeration will not claim every Windows service's private command line or binary was inspected. The CFD binding will explicitly account for wrapper and console-helper topology. Relevant unknowns will remain blocking. An exact host and explicit positive snapshot-age limit will be supplied; stale or malformed observations will refuse.

The same immutable config will additionally bind an operational object containing the selected executable, bundle, fixed output residence, queue lock, licence utility/server and source-rights/CFD-binding evidence paths and hashes. The production driver will validate those paths and current evidence, rather than substitute unbound CLI defaults. Its execution-bound source list and the config's single digest will cover this operational object without creating a second authoritative result store.

acquire_local_reservation will use the queue-compatible ASCII PID file and retain exact file identity and bytes. There will be no automatic context-manager release. release(no_owned_processes=...) will accept a real boolean only; false will preserve the lock, true will require unchanged owned identity before removal. The production caller will derive this boolean from the actual no-launch or settled-owned-process evidence; presence of an exception alone will never establish settlement.

Preflight will retain the raw selected inventory, coverage, classification digest and dispositions beside explicitly named conflicts. The legacy process_inventory field will contain the conflicts only and will carry an explicit scope label; an empty value will not describe an empty host. The ANSYS path rule will target the solver ansys/bin subtree, not every vendor installation directory. Licensing utilities will not receive a basename exemption or automatically become solver conflicts; any selected utility without an established disposition will remain UNKNOWN. The CFD binding will bind the host and every selected rank, wrapper and console-helper identity.

Operational capacity will require five consecutive one-second samples. In each sample, idle logical-core equivalents, calculated as logical_processors times (1 minus total CPU percentage divided by100), will be at least the one requested core plus one margin core. Available physical memory will be at least8GiB in every sample. The last sample and process snapshot will be no older than30seconds. These will be declared operational admission thresholds, not engineering acceptance limits or future resource guarantees. Initial failed/missing/stale observations inside the preflight callback will refuse before claim consumption. The immediate pre-launch rechecks in the launch wrapper will occur AFTER the durable claim; a stale observation, changed environment or changed lock at that point will consume the allowance even though the native process is not started. Integration tests will distinguish these two boundaries. Licence observations will likewise be fresh; current-release candidate availability will exclude the older incompatible increment and remain distinct from successful vendor checkout.

Preflight will retain the acquired queue lock's actual process ID, filesystem identity and read-back bytes, plus the operational owner binding. The legacy exclusive_seat_owner string alone will not establish reservation. The live lock will be checked against the handle's acquisition evidence immediately before launch. Only the owned, unchanged lock will be releasable after settlement. Local cooperative exclusion will not be described as a global floating-licence reservation.

Admission will compare canonical typed objects, so boolean values will not pass integer profile/budget fields. Capacity arithmetic will use finite Decimal values with explicit textual serialization. Review-bundle file digests will cover original raw bytes including a BOM; content comparison will use the existing helper's UTF-8-sig decoding. The exact code review will include cylinder_process.py and runner.py; synthetic supervisor tests will verify that no explicit environment override is passed. A licence parser fixture will retain the observed vendor output structure with private identifiers removed, alongside the private raw-source digest and transformation description. Review assertions that conflict with inspected source bytes will be dispositioned with that evidence, not adopted as new requirements.

Required integration tests will run the unchanged canary with synthetic launch/extract adapters: first-case success followed by durable scope refusal, first-case FAIL, prelaunch refusal, crash after claim before launch journal, mutated approval/environment, and unexpected second-launch attempt. A complete real first-case capture will remain a separate native observation. A selected-process CLEAR result will not itself satisfy licence, capacity or reservation preflight.
