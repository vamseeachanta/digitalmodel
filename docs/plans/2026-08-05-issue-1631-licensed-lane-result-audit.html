What the evidence refutes

The issue as filed named three OrcaFlex mock mechanisms as the cause. The workflow column above settles it: ten of the twelve runs are diffraction solves, one is OpenFOAM, and the single OrcaFlex workflow — orcaflex-strength-post — routes through none of the three modules named. There is no .sim file and no Mock simulation for artifact anywhere in the queue. The two FAIL runs were real licensed OrcaWave solves on a Windows host that produced physically invalid output.

A fix confined to those three files would have shipped green and turned zero of the twelve red.

What actually failed

src/digitalmodel/__main__.py:main() ended with a bare engine() whose return value was discarded, with no sys.exit on the engine-contract path. python -m digitalmodel <input.yml> therefore exited 0 regardless of what the engine concluded, on any host, licensed or not. Deckhand consumes that command through a thin subprocess.run wrapper, so that exit status was the entire success signal.

Separately, RunResult.validation_verdict was already computed, already typed against the closed five-value contract, and already attached to the result object — and was read by nobody. The router recorded result.status and dropped the verdict.

Three runs returned nothing and still passed

lr_acma_ff132001b7ad, lr_acma_8de9c018adbd and lr_acma_cd6fe46df9a4 have no returned_files key at all. The issue and the plan named only the first. A completed run that produced nothing now refuses, so all three would report non-zero today.

Disposition

  • No file in the queue repository was modified by this work. It was read-only throughout. This report is the durable record, and it lives in the repository that caused the defect.
  • The results are not deleted. They are the only evidence of the defect.
  • Annotation or quarantine of the twelve result files belongs to a follow-on issue against deckhand-licensed-runs-queue.
  • Re-running the twelve is not proposed here. It consumes the single OrcaWave/AQWA seat, and the two FAIL cases are expected to refuse, which produces no information this audit does not already record. Recommended only after the owner rules on the underlying physics.

Why WARNING still passes

Five of the seven validated runs are WARNING. A gate that refused WARNING as well as FAIL would have refused five of seven, read as rigorous, and made the lane unusable within a day. The boundary is not chosen from this distribution: it is the pre-existing vocabulary of output_validator._determine_overall_status, specified under #611/#625 long before any of these runs existed, and it is reused here unchanged.

That boundary has a known weakness, inherited knowingly rather than silently: it returns FAIL only when an issue string contains negative or missing. Under that rule, "added-mass matrix not symmetric at all 33 frequencies" scores as WARNING. Tightening it is a defensible stricter choice, and it is the owner's call in its own issue with its own evidence — retuning it here would be fitting a constant to the data being judged.
