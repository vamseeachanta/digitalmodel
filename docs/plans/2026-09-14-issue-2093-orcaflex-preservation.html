Proposed OrcaFlex preservation correction r3

The correction will address qualification issue 2093 and semantics issue 2104. Exact corrected-plan review will precede implementation; exact code and artifact review will precede candidate acceptance. No solver execution, API import, licence operation or historical evidence replacement will occur in this step.

Single General owner and precedence

GeneralBuilder will emit the only General section in 01_general.yml; GenericModelBuilder will retain other object handling and will cease emitting General. The existing General exclusion policy will transfer without widening its accepted keys. Explicit surviving general_properties values will win over typed simulation fallbacks. Each conflicting explicit value will produce a per-key warning, verified through caplog, so typed changes will not silently disappear. Thus explicit StageDuration, ImplicitConstantTimeStep and NorthDirection will win when supplied; simulation stages, time_step and north_direction will supply only absent values. No native equivalence will be inferred from the resulting dictionary.

The merge will begin with the filtered source keys in source order. UnitsSystem and any applicable User unit keys LengthUnits, MassUnits, ForceUnits and g will move to the prefix in that order. Missing fallback keys will be inserted immediately before the next existing key in GeneralBuilder's default reference order, or appended if no later default key exists. Source-only statics controls will therefore retain their order before the source DynamicsSolutionMethod rather than being appended after restart controls. The switch and its active dependent time-step key will be the only additional ordering exception. The original C07 statics-to-dynamics sequence and early-unit prefix will be asserted independently of value equality.

The merged ImplicitUseVariableTimeStep Boolean will select the active branch. With False, ImplicitConstantTimeStep will be emitted immediately after the switch and ImplicitVariableMaxTimeStep will be omitted. With True, ImplicitConstantTimeStep will be omitted even if a fallback or source key exists; a supplied ImplicitVariableMaxTimeStep will be emitted immediately after the switch. No variable maximum will be invented when absent. Dormant-key suppression will preserve the established builder contract; actual native settability will remain a separate readback requirement.

Source-specific wind key

EnvironmentBuilder will add Constant to the wind-dependent key policy only for VerticalWindVariationFactor. Presence will be tested separately from value: absent will remain absent; an explicit null will remain null; an explicit non-null value will remain that value. The dependent-key emission loop will follow the WindSpeed/WindDirection block. Existing type-specific wind exclusions will remain in force. Tests will set raw_properties as an attribute dictionary rather than assume a non-null mutable default.

The C07 source will support the exact serialized Constant-wind null and its position after WindDirection; it will not establish native assignment legality or physical equivalence of omission and null. Native load/readback will still be required to establish that property on the installed product before engineering parity can be claimed. The log interval 0.1 s, integration step 0.01 s and All statics participation will remain distinct controls; preserving them will not resolve other physical or lexical differences.

Bounded packaging change and provenance

scripts/prepare_mooring_qualification.py will add --source and prepare_bundle(output_root, *, source_path=SOURCE), with the existing default unchanged. A separately named checked-in derived spec will add only environment.raw_properties.WindType=Constant and environment.raw_properties.VerticalWindVariationFactor=null to the unchanged template semantics. The template and C07 received bytes will remain untouched. Both sources will be parsed with model_manifest.read_yaml, rejecting duplicate keys and YAML aliases. The comparison will descend into missing mappings to leaf JSON pointers and require the exact two-key allow-set for a derived source; any additional semantic or type change will refuse as unreviewed source difference. This check will prevent source selection from becoming an arbitrary physical-input override.

A source/derivation.json sidecar will record template_sha256, reference_sha256, source_sha256 and applied_keys using the two explicit JSON-pointer paths. These values will be computed from retained input bytes and checked differences, rather than accepted as caller assertions. The original template bytes will be retained at source/template.yml and included in manifest.files. contract_source_role=governing_template will identify the contract source in both derivation and reference-differences sidecars. The sidecar will precede final files enumeration. reference-differences.json will also precede final enumeration and will be included in the manifest hash list; its own input_files list will identify pre-report inputs and exclude itself to avoid a hash cycle. Manifest schema fields will remain unchanged. The existing qualification contract will remain unchanged: its source field will identify the governing template, while manifest.source and the derivation sidecar will identify the selected derived bytes. Its current source field will not be treated as a SHA pin; manifest verification already checks the retained selected source digest.

Packaging tests will isolate generator work with a synthetic stub and will test provenance, preserved source bytes, report coverage and extra-physics refusal. These tests will not stand in for real include-closure verification. Implementation validation will additionally run actual offline generation with Python hash seed 0, existing manifest verification, and the General/Generic/Environment regression suites. The existing qualification verifier's duplicate-assignment policy and RestartStateRecordingTest null-versus-empty mismatch will receive a separate explicit disposition before any change; this correction will not bypass them.

Owned changes and next executable action

Implementation will touch only the three OrcaFlex builders, the OrcaFlex preservation test, affected test_generic_builder.py and builders/test_general_builder.py contracts, the packaging script and a newly named derived spec. Shared initializers, ANSYS modules and original source evidence will remain outside the change. Following nonblocking corrected-plan review, the next code action will be the General-owner transfer with active-branch emission and the already failing order/precedence tests. The subsequent wind and packaging corrections will follow their failing tests. General assertions in the Generic suite will migrate to GeneralBuilder and a no-General assertion will protect ownership. Existing constant-mode and absent-wind passing cases will be reported as regression guards, not independent RED demonstrations. The contract-source role and RestartStateRecordingTest mismatch will receive explicit held dispositions. Exact code review will cover complete changed files and the schema/qualification dependencies; no historical review will substitute for current bytes.

Evidence to be checked

The companion disposition will bind source and test hashes, the original preserved plan/test copies, exact r1 review and captured r2 RED output. The remaining factual prerequisite will be native readback of the explicit Constant-wind null and the ordered General settings on the selected source. No parity or qualification result will be issued from offline equality alone.
