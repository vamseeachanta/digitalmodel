## Numbered findings

1. **MAJOR — P80 validates an external increment as if it were total hydrostatic restoring.**

   **Evidence:** P80:305 chooses `augment`; P80:369-382 computes `GM = K_SI[3][3]/(rho*g*V)` and requires agreement with geometric GM for the same matrix being emitted as external stiffness. `orcawave_backend.py:319` selects native displacement hydrostatics and `:362-375` separately emits external stiffness. `aqwa_backend.py:710-742` emits the separate FISK cards. Orcina's [displacement RAO equation](https://www.orcina.com/webhelp/OrcaWave/Content/html/Results%2CDisplacementRAOs.htm) distinguishes hydrostatic stiffness from external stiffness in the equation of motion.

   **Why wrong:** A legitimate zero external roll increment does not equal the box's nonzero hydrostatic C44. Conversely, emitting the geometric hydrostatic C44 as an augment adds it again. The required check would reject valid increments and can validate double-counting. A corrected total target need not equal the unmodified geometry's GM either.

   **Required change:** Represent and name `K_hydrostatic`, `K_external`, `K_total`, `K_target` and any correction separately. Apply the geometric GM oracle to the hydrostatic baseline under its stated assumptions, and verify composition with an independent `K_total = K_native_baseline + K_emitted_external` assertion. Add zero-increment, nonzero-mooring-increment and nonzero-target-correction cases.

2. **MAJOR — the proposed correction baseline is neither available through the cited API nor established as the native baseline.**

   **Evidence:** P80:311 obtains `K_baseline` from `deck_validation.validate_mesh`; P80:447 tests it with a stub. Actual `deck_validation.py:67-80` constructs a mesh-only `BodyConfig` and returns K33, K44 and K55, not a full 6x6. `src/digitalmodel/hydrodynamics/capytaine/models.py:71-83` defaults CoM to `(0,0,0)` and rotation centre to CoM. No declared vessel mass/CoG enters this call. `src/digitalmodel/hydrodynamics/capytaine/solver.py:114-117` passes rho but not the configured gravity into `compute_hydrostatic_stiffness`.

   **Why wrong:** Even a successful Capytaine calculation does not establish that its stiffness equals AQWA's or OrcaWave's native hydrostatics at the same mass, gravity, frame and mesh integration settings. The applied result is `K_target + (K_backend_baseline - K_Capytaine_baseline)`. Dependency availability alone cannot make that residual zero. Missing-mesh/error and incomplete-result cases are also not covered by the proposed absent-Capytaine guard.

   **Required change:** Specify a full baseline API, inputs, failure states, reference point and provenance. Either establish each native baseline against the independent calculation with a justified tolerance, or keep `correct_to_target` unsupported until a baseline for that backend is available. Include an intentionally mismatched baseline test; a stub subtraction test alone is insufficient. Add the necessary Capytaine adapter changes to ownership and tests if that route remains in scope.

3. **MAJOR — transformed numbers will be labelled with the original datum.**

   **Required change:** Separate declared input, resolved canonical and actual native datums, including coordinates and frames. Transform from canonical to the native datum before emission and record both. Define the direction of the offset `r` in P80:358-362. Require a nonzero-offset test through serialized matrix values and the native origin key. Retain fail-closed behavior for AQWA until its FISK datum is verified; coincident-origin testing cannot establish general reference support.

5. **MAJOR — AQWA serialization cannot meet the stated equivalence tolerance.**

6. **MINOR — the principal numeric oracle is correct, but its inverse test has an inconsistent tolerance and the claimed second oracle is algebraically dependent.**

   **Evidence:** P80:279-293, P80:457-459 and P80:462. Independent arithmetic from the stated dimensions gives:

   ```text
   V    = 100 * 20 * 5                 = 10000 m^3
   I_T  = 100 * 20^3 / 12              = 200000/3 m^4
   GM_T = 5/2 + (200000/3)/10000 - 8   = 7/6 m
   C44  = 1025 * 9.80665 * 10000 * 7/6
        = 117271189.583333... N.m/rad
        = 117271.189583333... kN.m/rad
   KG=10: GM_T = -5/6 m; C44 = -83765135.416666... N.m/rad
   ```

   **Why wrong:** The principal target `1.17271189583e8` and unstable test target are correct to their stated precision; no arithmetic MAJOR is justified. However, `GM_T == 1.1666667` within `1e-9` at P80:459 rejects exact `7/6`, whose difference is about `3.33e-8`. The second C44 form is an algebraic substitution, not an independent conservation law; it cannot detect a shared erroneous geometry/datum derivation. P80:266 also states free-heave behavior but the general check reads raw C44 without addressing heave-roll coupling.

   **Required change:** Use exact `7/6` or enough digits for the chosen tolerance, pass the fixture's rho and g explicitly into the report inversion, and describe the second-form check as algebraic consistency. Preserve the independent closed-form fixture oracle, without calling production derivation/conversion code to calculate its expectation. Restrict the raw-C44 GM check to the uncoupled upright fixture or define the appropriate heave-condensed coefficient for coupled cases. The plan does state CoG, upward z, radians and `F=-K xi`; those conventions are present rather than missing.
