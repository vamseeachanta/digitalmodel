## Findings

### MAJOR-1 — The run's log and its pass/fail verdict are still taken from files the same snapshot proves this run did not write

`runner.py:169` sets `log_file = out_file if out_file.is_file() else None`, and `runner.py:176` feeds that same file to `_detect_error`. Neither consults `previous_files` (`runner.py:149`) or `current_files` (`runner.py:170`), although `.out` is in `_RESULT_SUFFIXES` (`runner.py:33`) and is therefore already fingerprinted at both ends.

The result is an internally inconsistent attribution contract: one file can simultaneously be excluded from `result_files` as "not produced by this run" (`runner.py:171-174`) and published as this run's `log_file` and used as this run's error evidence. `workflow.py:61` forwards that stale path to the lane as `outputs.log_file`.

The false-success path: previous run leaves `<stem>.out` with no error markers; current invocation returns 0 without writing its `-o` target (failed redirect, licence checkout that exits 0, wrapper shim). Then `result_files == []`, `_detect_error` returns `None`, status is `COMPLETED`, and `workflow.py:65-77` raises on neither `failed` nor `dry_run` — the lane records a finish backed by zero current-run evidence. Nothing anywhere requires `result_files` to be non-empty for `COMPLETED`.

`tests/ansys/test_runner.py:70-83` locks this in. Its `subprocess.run` mock writes nothing; `model.out` is pre-written at `:73` before the run. The `FAILED` verdict it asserts is derived entirely from a stale file, and the correct fix would break it. Contrast the fidelity of the new test's mock, which writes its log inside the simulated run (`test_runner_result_capture.py:31`).

All evidence needed to gate this exists at `runner.py:169`. Cost of the fix is one comparison.

### MAJOR-2 — Unguarded filesystem I/O after the solve discards the record of a completed run

`_snapshot_result_files` calls `path.stat()` (`runner.py:221`) and `path.open("rb")` (`runner.py:224`) with no exception handling, and `_capture_result_files` calls `output_dir.iterdir()` (`runner.py:232`) likewise. The post-run call at `runner.py:170` sits **outside** the `try` that guards the subprocess (`runner.py:150-163`).

A `PermissionError` on a transiently locked `.rst`/`.db` (routine on Windows: AV scanning a freshly written FE binary; this repo's target platform is `WINDOWS x64` per both provenance files) or a `FileNotFoundError` from a file vanishing between `iterdir` and `stat` propagates out of `execute()`. The caller gets a traceback instead of an `ANSYSRunResult`, losing `return_code`, `stdout`, `stderr` and `duration_seconds` for a solve that may have consumed hours of the single shared licence seat. The module docstring's promise is a metadata-only *result*, fail-closed (`runner.py:9-13`); a raised `OSError` satisfies neither. The pre-run call at `runner.py:149` has the same exposure, less severely — it aborts before any work is done.

`_detect_error` has the same gap at `runner.py:205`: `out_file.read_text(errors="replace")` on a locked log raises, and on a multi-hundred-MB MAPDL `.out` it reads the whole file into memory.

### MINOR-1 — The hash mechanism the change exists to add is not proven by its test on POSIX

`runner.py:226` puts `st_ctime_ns` in the fingerprint. In the `overwritten` case (`test_runner_result_capture.py:26-30`), `os.utime` restores mtime but on Linux **ctime advances to now**, so the fingerprint differs on that field alone and the assertion at `:37` passes with the CSV digest deleted from `_snapshot_result_files`. The test is load-bearing only on Windows, where `st_ctime` is creation time. The comment at `:29` claims a guarantee the test does not establish off-Windows — and CI is the place this guard matters. Pin mtime *and* assert the digest path directly, or drop `st_ctime_ns` from the tuple so the stated mechanism is the one under test.
