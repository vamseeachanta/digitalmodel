Solver outcome retention audit

Summary

The canary wrapper previously raised when its final outcome write failed, discarding the structured return value after attempts had been consumed. The wrapper now returns an INCOMPLETE disposition with the recording error, retains the original execution reason, and preserves existing or partial evidence. The diagnostic exit check rejects that unretained outcome. These changes meet the consumed-attempt/no-retry contract in issue 2128 for the synthetic failure paths exercised below; durable storage is not established when an outcome write fails.

Scope and basis

This is a source audit and synthetic fault analysis, not a solver campaign. The originating defect is documented in issue 2121 and its reusable contract is recorded in issue 2128. No equation, engineering coefficient, acceptance tolerance or licensed reference value is introduced. Expected counts are independent event traces in the test docstrings: a launch failure after the first claim consumes the first attempt; a completed synthetic sequence consumes its complete case order; recording errors cannot reverse either history. Each wrapper is classified from its own source contract rather than assuming that every wrapper uses a consumed-attempt ledger.

The source inventory is based on 6476218e plus the canary and diagnostic corrections in this change. Later source revisions will require a fresh audit before these dispositions can be reused.

Regression evidence

The retention regression module contains seventeen synthetic cases. Nine cases reproduced the unguarded canary write and the caller exit-code gap before implementation; all seventeen passed after correction. The tests inject no native adapter. Existing and partial outcome bytes and claim bytes are checked for preservation. Both pressure ordinals retain their no-readmission behavior when terminal and outcome writes fail together.

Limits and next work

The inventory is bounded to the linked entry points; it is not an exhaustive repository audit. A failed write can leave an absent, partial or unverified outcome file; the structured return is available for independent retention, not proof of durability. A receipt written before a readback failure may still contain its earlier status, so callers must use the returned recording error. Existing evidence is never rewritten to repair that discrepancy. Process termination, abrupt interpreter exit, filesystem-wide failure and engineering qualification remain outside the synthetic evidence. Failures between approval consumption and the per-attempt record retain their existing behavior and require separate coverage.

Existing hash-bound runtime bundles will require their normal source rebinding and review before the changed wrapper can be used for execution.

Follow-up work under issue 2128 will reproduce the listed persistence and cleanup candidates at their actual callers before changing their independent retry and resume policies. Other solver and automation entry points will be inventoried separately. Independent second-provider review will precede merge; this audit does not claim that review has occurred.
