Issue #1959 — solver-start evidence

A freshly emitted, unpatched interFoam case starts and advances. Recorded 2026-08-04 on the CFD node.

Why this artifact exists

A dry-run rc=0 proves rendering, not running. The regression tests in test_solver_contracts.py assert that the emitted dictionaries contain the keys interFoam needs, but the emitter renders from the same contract those expectations describe, so that layer proves consistency rather than correctness. The only oracle whose verdict does not depend on the author having guessed the requirement list correctly is the solver itself.

This page records that run. It also records the negative control on origin/main, because a passing run means nothing unless the same procedure fails on the unfixed builder.

The run is genuinely two-phase: MULES is correcting alpha.water and the phase-1 volume fraction holds at 0.50012 for the half-full tank, so the alpha equation this issue is about was actually exercised rather than trivially skipped over an empty domain.

The tree that ran is the tree the builder emitted

A solver-start criterion is satisfiable by a patched tree — which is the exact failure mode this issue is about, and it would be embarrassing to reproduce it inside its own fix. What the oracle found that inspection did not

Three defects were identified by reading the dictionaries against the v2312 tutorial. The solver then found three more, in sequence, each one only reachable once the previous was fixed. That progression is the argument for this artifact existing at all.

#DefectFound by
1fvSolution: alpha.water lumped into a turbulence regex group, no MULES controls, no cAlpha; p/pFinal emitted instead of p_rgh/p_rghFinal/pcorr inspection
2fvSchemes: single-phase div(phi,U) and div((nuEff*dev(T(grad(U))))) under default none inspection
3fvSchemes: div(phi,alpha.water) emitted, but the alpha equation looks up div(phi,alpha) inspection, against the tutorial
4fvSchemes: no wallDist block, which kOmegaSST requires solver start
5fvSchemes: ddtSchemes default backward, which interFoam's alpha equation rejects at run time solver start
6fvSolution: no UFinal, which PIMPLE looks up on its final corrector solver start

Defects 4, 5 and 6 are invisible to any test that compares the emitted dictionary against a declared requirement list, because they were absent from the requirement list. Only running the solver surfaced them.

Value provenance

Every literal introduced traces to the pinned v2312 installation or to an input the case already declares. Nothing was taken from the node's hand-authored case directories, where a sweep found 139 fvSolution files in 18 distinct variants.

patch_case.sh on the node uses cAlpha 1.5 and nAlphaSubCycles 3. Neither value was adopted, and the successful historical run on that node used cAlpha 1 — so the script is not the source of the working evidence and importing from it would have meant adopting a fitted constant of unknown provenance.

Reproducing this

ssh undi@gpu-claw
openfoam2312 -c "cd <checkout> && python3 -m pytest \
    tests/solvers/openfoam/test_case_runnable.py -v"

The Layer 2 test skips itself where interFoam is not installed, so CI will report it as skipped. A skip proves nothing, which is why this artifact is committed rather than relied upon as a green tick.

Two launcher traps on this node, recorded so the next run does not rediscover them: set -u kills any OpenFOAM launcher, because etc/bashrc dereferences WM_PROJECT_DIR before setting it; and sourcing etc/bashrc directly from a non-interactive script trips pop_var_context: head of shell_variables not a function context. Use the ESI-provided openfoam2312 -c wrapper instead.
