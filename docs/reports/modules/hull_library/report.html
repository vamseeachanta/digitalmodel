1. Executive Summary

The synthetic rectangle is evaluated for origin-based uniform and independent-axis panel scaling. The module quantities are compared with perpendicular-edge hand calculations in the worked example table. This is a bounded numerical example; the package's wider interfaces remain NOT_EVALUATED here.

Reproducibility does not establish physical validation. The next engineering step is a separately scoped qualification with a declared physical geometry, response provenance and convergence criterion.

2. Introduction

The source-linked inventory separates implemented interfaces from independently checked methods. INDEPENDENTLY_CHECKED applies only to the stated rectangle, positive factors and floating-point budget.

HullProfile and HullStation describe offsets and dimensions; HullMeshGenerator.generate accepts a profile and MeshGeneratorConfig and returns PanelMesh. HullLookup.get_hull_form returns a dimensional match, not a response. RaoRegistry.get_raos returns references; load_rao_data checks stored integrity. RAODatabase.query filters stored entries. HullCatalog.compute_motions and compute_accelerations consume response data. These routes are documented by source inspection; no hull is generated and no response lookup or response calculation is executed for this report.

3. Data Basis

All coordinates, connectivity, reference points and factors are synthetic assumptions from the preserved worked example, Inputs and Derivation. Model coordinates are assigned metres; areas use square metres. Factors and normals are dimensionless. Connectivity uses ordered, zero-based indices.

The complete input and output values are bound in Table 5.1: source.vertices, source.reference_point, source.panels and the factors in each case. The source factor is the identity transformation. Reference points are scaled about the Cartesian origin; they are not scaling pivots.

No measured, historical or response-table data are consumed. No physical constants or standards tables are needed. The tilted rectangle is planar with perpendicular edges; it does not represent a closed wetted hull.

4. Theory and Equations

The equations follow Cartesian geometry in the existing Derivation section. The independent calculation uses edge lengths, while PanelMesh computes the sum of triangle areas.

E1: P′ = diag(sx, sy, sz) P and R′ = diag(sx, sy, sz) R.

E2: AB′ = B′ − A′, AD′ = D′ − A′; AB′ · AD′ = 0. Length = sqrt(edge · edge). Area = |AB′| |AD′|. Total area is the sum of panel areas.

E3: n′ = (AB′ × AD′) / |AB′ × AD′|, using the specified corner winding.

E4: centre = arithmetic mean of the corner coordinates.

E5: connectivity is copied; vertex and panel counts are preserved.

The comparison budget is 64ε max(1, |q|), in the unit of each scalar q, where ε is binary64 machine epsilon. The dyadic coordinate products and edge differences are exact at these magnitudes. Cross products, squared norms, square roots, the triangle sum and normal division require fewer than 64 scalar operations; the nonzero components have no subtractive cancellation for this rectangle. The operation allowance supplies a roundoff budget for this example, not a fabrication tolerance or a hydrodynamic acceptance criterion. Connectivity and counts are checked exactly. No wider coordinate range is qualified.

6. Validation Evidence

Report tests compare unrounded quantities with an independent Cartesian oracle under the stated roundoff budget and check the displayed units and equations. Fresh public calls corroborate the computed record. A controlled area mutation checks that visible results and differences change. Two output directories are rebuilt and compared byte for byte with the delivered HTML, source and change records.

Existing documented example tests and existing scaler tests remain separate regression coverage. The test definitions are evidence locators; live execution counts are reported with the change, rather than generated as an unobserved pass claim.

Output comparisons use one decimal place; topology and counts remain integers. Embedded calculation data use the same display precision. Full-precision assertions use calculate() results before rendering. Rounded equality alone does not satisfy the numerical criterion.

7. Limits of Use

  • physical hull suitability: NOT_EVALUATED
  • hydrodynamic responses: NOT_EVALUATED
  • response-table provenance: NOT_EVALUATED
  • mesh convergence: NOT_EVALUATED
  • solver qualification: NOT_EVALUATED

Geometric scaling does not scale hydrodynamic responses. Response frequency, heading, amplitude, phase, coordinate-frame and loading-condition conventions require independent evidence before reuse. No response values are obtained here.

Mesh generation, refinement, topology repair, geometry kernels, external meshing backends and solver execution are outside this worked computation. Existing tests of those interfaces are not adopted as numerical qualification in this report.

8. Recommendations

A separate qualification should declare geometry provenance, loading condition, units and coordinate conventions, compare mesh properties against an independent geometry, and prescribe convergence and response acceptance criteria before any engineering response is adopted. Backend selection and solver qualification require separately routed work.

Source-review findings: validate_scaled_mesh uses centroid-radial normal checks and an origin-relative draft estimate; these do not establish outward winding of a general hull. Shallow metadata copies do not promise nested independence after later edits. Dimensional nearest matching and response filtering do not establish physical suitability. These concerns are recorded for broader qualification; production behavior is unchanged. See scaling and validation interfaces and module evidence and known limits.
