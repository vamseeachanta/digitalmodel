1. Executive Summary

The geographic information system (GIS) module is a set of coordinate, geometry, layer and exchange tools. Analysis is performed to determine whether its horizontal coordinate interface reproduces a documented map example; key results are summarized below.

  • A published map coordinate is reproduced at centimetre display precision.
    • The input at 2° east and 49° north is mapped to easting 222638.98 m and northing 6274861.39 m [2].
  • The example supports map preparation within the stated horizontal-coordinate scope.
    • The pole is excluded: no finite northing exists at 90° latitude [1]. A survey reference and measurement tolerance remain required before engineering distances are accepted.

2. Introduction

Geographic positions are transformed into map coordinates by the public coordinate interface. The main workflow is demonstrated from an explicit source reference through forward and inverse transformation.

The package also provides point geometry, spatial searches, tabular feature and well layers, raster and temporal layers, file exchange, mapping exports and imagery preparation. These facilities support locating and exchanging engineering data; structural capacity, asset condition and survey quality are not calculated by this example.

3. Data Basis

The input basis is taken from the public Web Mercator example and its reference definition. Numerical agreement is assessed against the precision printed in that example; engineering suitability is assessed separately.

Source positions use the World Geodetic System 1984 geographic reference. Target positions use its Web Mercator map reference. The European Petroleum Survey Group registry identifiers are given in the interface record in Section 9.2. The interface fixes horizontal order as longitude then latitude on input, and easting then northing on output.

The projection radius is 6378137 m [3]. The central meridian and the false coordinate offsets are zero [2]. The acceptance tolerance for comparison with the published coordinates is half a centimetre, derived from their centimetre rounding; it is not a survey or map-scale accuracy criterion. The data register in Table 3 identifies inputs needed for site use.

4. Theory and Equations

The horizontal mapping is evaluated with spherical Mercator equations using the ellipsoid semi-major axis as radius. The geographic latitude is used directly, as defined for Web Mercator [2].

x = a(λ − λ₀); y = a ln[tan(π/4 + φ/2)] [1]

Here x is easting in metres, y is northing in metres, a is the projection radius in metres, λ is longitude, λ₀ is the central meridian and φ is latitude. Angular arguments are in radians; π denotes the circular constant. Degree inputs are converted by multiplying by π/180 [1].

λ = x/a + λ₀; φ = π/2 − 2 arctan[exp(−y/a)] [1]

The inverse recovers longitude and latitude in radians before conversion to degrees. The equations use zero false offsets for this example [2]. The logarithm diverges at either pole; the northern boundary is drawn in Figure 2 [1].

k = 1/cos φ [1]

The symbol k is local linear scale on the reference sphere. It increases with latitude. This spherical relation explains map distortion; Web Mercator on an ellipsoidal Earth is not a conformal ground-distance model [2]. No ground-distance correction is applied or accepted here.

7. Limits of Use

The calculation scope is restricted to horizontal map coordinates and the documented example. No acceptance of site accuracy, height, distance, area or operational clearance is assigned.

Map metres describe the projected plane. They are unsuitable as uncorrected ground distances away from the projection origin; the spherical scale relation and the ellipsoidal caveat in Section 4 govern this limitation [1] [2]. The poles remain outside the finite mapping domain. A finite library return value at a pole is not evidence that the singularity is removed.

Source-reference labels, coordinate order and units are caller responsibilities. The low-level transformer does not request strict error handling from the projection library; non-finite output and out-of-area inputs require explicit checks in an application. A horizontal transformation with an added height does not establish a vertical datum transformation.

The geometry and spatial-query interfaces also need care: Euclidean distances use coordinate units, spherical searches expect geographic degrees, and bounding boxes are axis-aligned. A box spanning the date line requires an explicit geographic treatment. Automatic transverse-Mercator zone selection uses regular longitude bands; special-zone and polar use requires a qualified reference choice. These implementation limits are located in Section 9.2.

8. Recommendations

The coordinate interface is recommended for the demonstrated map-preparation calculation with explicit reference labels. Additional input qualification is required before the outputs are used for survey, clearance or engineering measurement.

For each engineering dataset, record the horizontal reference, axis order, units, coordinate epoch and positional uncertainty. Supply a vertical reference when height matters. Check the reference area and reject non-finite results before export. These controls address the reference and domain limitations in Sections 3 and 7.

For a distance or area decision, select a qualified local projection or an ellipsoidal geodesic calculation, and assess its error against the supplied engineering tolerance. The projection distortion in Section 4 is the reason for this action [1] [2]. At a pole, select a polar reference instead of accepting Web Mercator output [1].

Extend the present numerical controls with dated survey-control coordinates, explicit area checks, vertical-reference tests and date-line cases before extending the report's acceptance scope. The missing data are listed in Table 3; no numerical survey tolerance is assigned without that basis.

9.2 Interface and repository records

The public entry point is CoordinateTransformer with transform_point or transform_points. The source identifier is EPSG:4326 and the map identifier is EPSG:3857. The complete example is calculated by the generator; the following minimal call shows its order.

from digitalmodel.gis import CoordinateTransformer
forward = CoordinateTransformer("EPSG:4326", "EPSG:3857")
easting, northing = forward.transform_point(2, 49)
inverse = CoordinateTransformer("EPSG:3857", "EPSG:4326")
longitude, latitude = inverse.transform_point(easting, northing)

10.2 Quality pre-flight evidence

The report test checks three literal hand-calculated anchors, the published coordinate pair, every bound result, the plotted samples and the rebuilt artifact at displayed precision. A headline coordinate is recomputed from the displayed inputs. Links and section targets are checked; the stylesheet is compared with the layout exemplar.

Text is read and written explicitly as Unicode, with fixed line endings. The report tests are executed with the implicit Unicode mode unset. Browser interaction, print rendering, external survey data and imagery retrieval are not tested by this report. Comment saving, export, reload and chart focus events are exercised with simulated file handles and document elements. Their operation in a particular browser remains untested.

10.3 Not covered

Raster operations, temporal data, well-specific metadata, external mapping exports, imagery retrieval and rendering, and environmental-source selection are outside the worked calculation. The repository contains additional tests for those areas; no execution or numerical acceptance is claimed for them here.
