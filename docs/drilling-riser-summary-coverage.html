Criterion summary coverage contract

postprocess.evaluate.summarise reports supplied final checks and their coverage. It changes no criterion, limit, factor or acceptance value and does not establish design acceptance.

Inputs and reconciliation

The positional iterable of (case_id, CaseCheck) is retained. Two optional keyword arguments make coverage explicit: expected_cases maps criterion ID to sensitivity group to applicable logical case IDs; ledger_outcomes maps logical case ID to its final run outcome.

Build expected sets from the run manifests and criterion applicability, including cases without checks. Use aggregate.collect to reconcile attempts: the latest ledger record governs and a manifest case with no ledger is retained as missing. Map returned records to ok and issues to their returned status. Verify result digests with load_verified before evaluation. For seeded cases, reconcile all expected seeds into the logical case before summarising; an incomplete seed set must not become an ok logical case. The summary does not read files or infer applicability.

Each criterion/case pair has exactly one final check. Duplicates, invalid check statuses, duplicate IDs within a group, and observed cases outside explicit applicability raise ValueError. Groups may overlap; row counts use their union, so a case is counted once per criterion.

Returned fields per criterion and group

FieldMeaning
counts, governing, max_uExisting fields describe supplied checks; screening never governs.
observed_statusFAIL if any supplied check fails; otherwise PASS if any passes; otherwise NOT_EVALUATED. This field alone says nothing about coverage.
expected_cases, recorded_casesSorted applicable IDs and supplied check IDs. Expected cases are null when undeclared.
final_outcomesFinal ledger status for each expected case (observed cases if no expected set). Missing entries in a supplied ledger mapping become missing. Values are null when the mapping is omitted.
missing_cases, missing_countExpected cases without a check or with a final outcome other than ok. Both are null without an expected set. Without ledger evidence they count absent checks only, not verified final-result coverage.
unevaluated_casesSupplied NOT_EVALUATED check IDs, including unsupported criteria. These need not have missing solver results.
coverage_completeTrue only for a nonempty expected set with every check, every final outcome ok, and no NOT_EVALUATED check. False otherwise; null if either coverage input is omitted.
statusObserved FAIL stays FAIL independently of coverage. PASS requires complete coverage and observed PASS. Otherwise NOT_EVALUATED.
groupsThe same fields per declared sensitivity group, without nested groups. Empty when applicability is not supplied.
Table 1. Summary fields. Null denotes unknown, not zero.

SCREENING checks count as recorded coverage but never yield PASS by themselves. Empty selections are NOT_EVALUATED; a completely undeclared empty input returns an empty dictionary. A failed solve is a coverage gap, not an engineering FAIL. A supplied stale PASS cannot overcome a failed final ledger outcome.

Compatibility and sources

Existing callers in test_evaluate.py and test_w510_significant_range.py keep the positional interface; postprocess/__init__.py still exports the function. A formerly passing summary without both coverage inputs now returns NOT_EVALUATED. Consumers wanting the old observational value can inspect observed_status together with coverage_complete.

Status vocabulary is defined in src/digitalmodel/drilling_riser/postprocess/evaluate.py:32; final ledger and missing-case semantics are defined in aggregate.py:3-8 and aggregate.py:64. No new status words or engineering constants are introduced. Tests use synthetic records and case/group identifiers already present in the evaluator and aggregation tests.

The configuration-specific consumer is outside this public repository; parity with its implementation is not established. The public contract is covered by test_summary_coverage.py.
