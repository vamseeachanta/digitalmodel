CI runtime and baseline freshness policy

Summary

The timeout limits bound resource use for the 19 logical jobs in the 12 workflow files. Matrix expansion can create more executions. The limits are explicit resource allocations; successful completion within them is not established by timing measurements. The authoritative allocations, margins, job assignments and freshness rationale are recorded in runtime-policy.json, version 1.

Concurrency and coverage

Incremental push runs in quality-gates.yml and quality-gates-by-domain.yml use distinct groups for each run; superseded pull-request runs for the same workflow and ref cancel. The pages and publish deployment groups serialize without cancelling an active execution. These settings do not establish deployment completion or a bound on queue time.

The Full Matrix Sweep workflow runs nightly or manually; a newer sweep cancels an older sweep for the same ref. It has no push trigger. Incremental domain checks select the touched shards, with a full matrix fallback when the push base is unavailable. A pass for the selected shards supplies no execution evidence for omitted shards.

Timeout allocations

Each timeout is the sum of its work allocations and margin. The allocations represent the maximum resource allowance chosen for that class of work, not predicted phase durations. The margin permits variation within the cap. A timeout remains a failed or incomplete execution; it does not qualify a result or permit a check to be skipped.

Publication duration is unmeasured. Aggregate shard time is not a measure of the publication job: parallel shards, setup, test selection and packaging are different operations. The 180-minute cap does not establish that publication will finish within it. Cold-cache completion within the other new caps also remains unverified. Completed hosted runs are needed to assess those caps; any later adjustment requires timing evidence and an updated policy basis.

Baseline freshness

The full matrix sweep is scheduled daily and can be dispatched manually. A 24-hour cadence plus a six-hour grace period gives a 30-hour inclusive freshness limit. Six hours is one quarter of the daily cadence and is chosen as the tolerated scheduling and completion variation; it is not an observed delay or a hosted scheduling guarantee. A completely missed daily sweep is not covered by this allowance.

Baseline selection and comparison use this limit. Selection checks run updated_at; comparison also checks shard completed_at. Future timestamps and ages above the limit are rejected. The newest eligible completed main sweep must have available evidence; absent evidence does not permit fallback to an older successful sweep. Completed manual and scheduled main sweeps qualify; historical main push sweeps remain supported by the reader. This reader compatibility does not add a push trigger to the full-sweep workflow.

Policy checks and limits

Workflow policy tests derive each expected timeout from the JSON allocations and margin and check complete job coverage against the committed inventory. Existing negative controls reject missing, zero and increased timeouts. Baseline tests bind the freshness constant and workflow comparison argument to the same documented cadence and grace period; the boundary cases include the inclusive limit, stale evidence and future evidence.

These checks establish agreement between the policy and configuration. They do not establish hosted completion, publication duration, mergeability or successful execution of omitted domain shards. Full-sweep coverage comes from nightly and manual runs; touched-domain results cover their selected shards only.
