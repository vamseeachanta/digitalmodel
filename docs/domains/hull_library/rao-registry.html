RAO registry identity and upgrade

RaoRegistry stores JSON datasets in per-hull directories and references in registry.yaml. This is separate from RAODatabase and its fixture population workflow.

Registration and corrections

New filenames are sha256_<digest>.json. The standard-library SHA-256 digest covers canonical JSON: keys sorted, compact separators, default ASCII escaping, UTF-8 encoding, and non-finite numbers rejected. The complete payload participates except the registration date. Hull, solver, exact draft, loading condition, benchmark revision, headings, frequencies, amplitudes and phases therefore distinguish datasets. Draft and headings are stored as floats; arrays retain their serialized numeric values. JSON integer and float encodings are distinct. Units and field definitions remain those of the registry payload.

Identical serialized content returns the original reference and date without rewriting the file or index. Different content, even under the same hull, solver, draft, condition and benchmark revision, creates a retained revision. Corrections never replace earlier content. Existing digest files are verified before reuse; corrupt history is not repaired by re-registration.

New revisions appear first in lookup results; an identical repeat does not reorder them. The existing inclusive 0.5 m draft lookup tolerance remains only a search rule. It does not determine storage identity. Conditions and benchmark revisions can be selected from the returned reference metadata.

Historical references

The RaoReference schema and existing relative-path anchor (the registry directory's grandparent) remain unchanged. New references use forward slashes and carry their digest in the path. Loading verifies content against that digest and checks all reference metadata, including the original date. Missing, unreadable, changed or mismatched data raises ValueError with an integrity message. References outside this registry are rejected. Preserve the original reference when checking history; the index is not a trusted replacement for it.

Legacy upgrade

Version 1.0 indexes remain readable. Their entries remain discoverable and retain their metadata when new entries are added. Legacy date-based filenames carry no original content digest: loading such a reference now fails explicitly, even if its current JSON looks plausible. This cannot determine whether an older writer already overwrote the original dataset. No legacy reference or dataset is automatically renamed, migrated, deleted or declared qualified.

For reuse, independently establish the legacy dataset's intended identity and provenance, then register the verified inputs to create a new reference. Preserve the old reference and evidence separately. A digest establishes content integrity, not engineering qualification, coordinate conventions or source validity.

Caller behavior and limits

analysis_setup._attempt_rao_lookup still consumes the first match; this now means the newest retained revision. Its existing exception handling returns unavailable data for integrity failures, including legacy references. Catalog linking continues to attach all matching references. Callers needing a specific condition must select that reference explicitly. Registration supports single-writer use; concurrent index transactions and legacy data recovery are not provided.
