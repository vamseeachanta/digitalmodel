ANSYS response acceptance criteria

The offline evidence adapter evaluates equilibrium, convergence and strength separately from native execution and independent reference agreement. Engineering lookup requires explicit intended-use requirements in the digest-bound verification register. Existing diagnostic packages remain diagnostic; import alone establishes no engineering qualification.

Method and evidence contract

Source: ENG-ANALYSIS-CRITERIA, Revision 1 (2026), AC-01, AC-07 and AC-08; ANSYS analysis workflow, Revision 1 (2026), Extract and verify. No engineering constants or default acceptance limits are supplied. The numerical operations are exact decimal ordering: observed ≤ limit (le), observed ≥ limit (ge) or |observed| ≤ limit (abs_le), with equality passing. An absolute comparison requires a nonnegative limit and preserves the signed observation in its decision record. Values and limits share the declared unit; no conversion or interpolation is performed.

Each verification entry adds acceptance_criteria, a mapping with optional equilibrium, convergence and strength records. Each supplied record requires exactly criterion_id, quantity, unit, observed, limit, comparator, source and nonempty evidence. The source is an object with exactly document, edition and clause strings; the clause identifies the clause/table or independently recorded derivation. Empty strings and case-insensitive placeholders such as TBD, n/a, -, unknown and x are rejected in every source field. Evidence references use the existing logical ID and SHA-256 resolver protocol. Their bytes are checked on every evaluation. Structured citations and matching bytes do not establish source applicability or engineering authority; the independent checker remains responsible for the source and derivation of the observed quantity, limit and units.

acceptance_requirements maps each permitted intended use to a nonempty list of required criteria. Equilibrium and convergence are always required. A strength decision additionally lists strength. A demand-only use may omit strength explicitly, retaining NOT_EVALUATED for capacity readiness. Any supplied FAIL, including a strength failure for demand-only use, blocks qualification. This policy is frozen with the verification register; an ordinary query cannot supply or override it. Strength observations, when supplied, must equal the signed queried response value, definition and unit; abs_le applies the magnitude comparison without changing that binding. A strength criterion shall therefore use the same quantity as that response, rather than an unrelated utilization.

A missing record, observed value or limit yields NOT_EVALUATED; a valid comparison yields PASS or FAIL. Malformed records, unknown record fields or criterion names, nonfinite values, unsupported comparators and unavailable or changed evidence raise ValueError. A null response value also raises ValueError. Any required check other than PASS blocks engineering lookup. Independent comparison, rights, retained-native evidence, current publication authority, review findings and withdrawal checks remain required.

Worked offline example: comparison protocol

Inputs below are invented software-test values, not engineering data or design limits. Independent hand calculation: 12.5 is less than 13, so the supplied strength comparison passes; 12.5 exceeds 12, so changing the limit to 12 fails. Equilibrium and convergence are absent and remain NOT_EVALUATED. The result does not qualify any case. The source file is created only in a temporary directory configured through the launch environment.

from pathlib import Path
from tempfile import TemporaryDirectory
from digitalmodel.ansys.analysis_criteria import evaluate_criteria
from digitalmodel.ansys.analysis_records import digest_bytes

with TemporaryDirectory() as directory:
    basis = Path(directory) / "basis.txt"
    basis.write_text("Synthetic comparison example, revision 1: 12.5 < 13; 12.5 > 12.",
                     encoding="utf-8", newline="\n")
    strength = {
        "criterion_id": "synthetic-comparison", "quantity": "test scalar",
        "unit": "MPa", "observed": "12.5", "limit": "13", "comparator": "le",
        "source": {"document": "Synthetic comparison example", "edition": "Revision 1",
                   "clause": "Independent ordering"},
        "evidence": [{"id": "basis", "sha256": digest_bytes(basis.read_bytes())}],
    }
    result = evaluate_criteria({"strength": strength}, {"basis": basis})
    assert result == {"equilibrium": "NOT_EVALUATED",
                      "convergence": "NOT_EVALUATED", "strength": "PASS"}
    strength["limit"] = "12"
    assert evaluate_criteria({"strength": strength}, {"basis": basis})["strength"] == "FAIL"
    print(result)

Lookup and migration

lookup(...) returns acceptance_results only after the existing qualification gates and the required checks pass. Each check returns an object containing status and every supplied criterion field: ID, quantity, unit, observed value, limit, comparator, structured source and evidence. Decimal input strings retain their precision. An absent check returns NOT_EVALUATED with null criterion fields, including unresolved capacity for a demand-only use. Diagnostic retrieval removes this key even if it is embedded in a package response, and continues to return unqualified responses without requiring a register. Historical registers lacking explicit requirements or structured sources cannot qualify an engineering response; a new register digest and package revision bound to current authority are required. Consumers of the former bare-status mapping shall read each check's status field. Merely adding passing labels is insufficient.

Tests cover both inclusive boundaries, exact magnitude comparisons of negative responses, high-precision ordering, null versus zero, missing requirements, placeholder and malformed sources, unknown fields, supplied optional failures, changed evidence, response binding, complete decision records and diagnostic preservation. Existing retained results are neither rewritten nor newly qualified. Native execution, new campaigns, physical validation, source authentication and automated determination of criterion applicability are outside this offline implementation.
