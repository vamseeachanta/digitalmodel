Fixed-bottom wind turbine analysis workflow

Summary

Offline preparation and stored-export processing are implemented. Native turbine results and engineering acceptance remain NOT_EVALUATED.

Scope and sources

The raw model, library specification and steady template are distinct representations. The inventory records their exact-byte digests rather than asserting equivalence.

The generator input L2 describes a smaller reference turbine; L23–26 set usable time, hub height and grid dimensions. It is not a proven recipe for this rotor. The template and turbulent route also change the speed and controller arrangement. Their differences cannot be attributed to turbulence alone.

The public turbine definition is IEA Wind Task 37, Systems Engineering in Wind Energy — WP2.1 Reference Wind Turbines (May 2019), section 5, Offshore Wind Turbine. The public model repository links its OrcaFlex implementation to the vendor examples portal. Equivalence of the held model to the report remains to be established. No coefficients or acceptance limits are transcribed from that publication.

Method and case matrix

Prepare baseline, softened and stiffened soil for each of steady and turbulent wind: six dynamic case slots. Baseline factor one is the identity K_case = K_held. Soft/stiff multipliers have no defaults: 0 < softened < 1 < stiffened is only the definition of the comparison labels, not a soil acceptance range. A cited engineering basis is required before selecting levels. The synthetic fixture uses arbitrary arithmetic levels only.

The issue's approximate analysis count is a planning estimate. Reusing statics/modal results between wind/control arrangements requires native readback proving compatible equilibrium and preload; this workflow does not assert that those operations can be shared.

  1. Freeze the representation, source digests, defining reference, environmental settings, wave seeds, soil-level basis, controller and wind route. Confirm mesh, sample interval and production-window adequacy.
  2. Prepare model changes separately. The workflow writes reports and analysis JSON only. Review all distributed stiffness changes, including rotational coefficients; retain constraint connections, DOFs and damping.
  3. After separately authorised native execution, retain solver version, static convergence evidence, modal shapes, input/controller/wind digests and native time histories. No solver is started by this workflow.
  4. Export global force and moment components at the mudline section using one recorded sign convention. Convert to kN and kN.m before export. Do not substitute tower-base loads, and do not translate loads without accounting for the moment arm.
  5. Assign stable mode_key labels from reviewed shapes and record shape_evidence for every mode. Provide tower and monopile labels as supported by the native shapes. Mixed modes may have descriptive labels; this workflow does not infer localization from frequency order.
  6. Reduce samples in the inclusive window. Sample mean = sum(x)/N, from NIST/SEMATECH e-Handbook, online edition read 2026-10-20, section 1.3.5.1, Measures of Location. Minimum, maximum and absolute peak are sample order statistics, not long-term extremes. A sample mean is not a time-weighted mean for irregular sample intervals.
  7. Compare within a wind/control arrangement by reviewed modal label. The relative-change definition is (variant − baseline)/baseline; report percentages to one decimal place. Zero baseline loads give NOT_EVALUATED, not zero change. Matching windows, signs, non-soil basis fingerprints and mode-label sets are mandatory.

Stored-export contract

JSON is a list of case records. The synthetic input is executable documentation of the schema. Required fields:

FieldContract
case_id, representation, soil_factorMatch the prepared case. For example steady_baseline uses template and identity soil factor.
synthetic, solver_versionExplicit boolean and nonempty version. Every record in one report has the same synthetic status and solver version.
input_sha256Lower-case SHA-256 of the actual solved input bytes, including soil changes. Synthetic records use an explicit dummy digest.
comparison_basis_sha256Fingerprint of the complete unchanged comparison basis: non-soil model settings, wind and controller files, wave/current definition and seeds, equilibrium/preload treatment, numerical settings and exporter version. Canonicalize a sorted-key JSON manifest and hash its UTF-8 bytes; only the declared soil multiplier and resulting soil coefficients are excluded. Retain that manifest with native evidence. Different fingerprints prevent sensitivity calculation.
soil_factor_sourceNonempty source and locator for the selected soil level; synthetic inputs identify their arbitrary arithmetic basis.
frame, origin, force_unit, moment_unit, load_conventionglobal, mudline, kN, kN.m, and a nonempty sign/action description. Axes are the model's global axes; no hidden transformation is performed.
window_s, samplesInclusive start/end with positive duration. Samples cover the whole window, have strictly increasing time_s and finite fx, fy, fz, mx, my, mz. At least two selected points are required to describe a history; this is not an adequacy limit.
modesUnique nonempty mode_key, finite positive frequency_hz, nonempty shape_evidence. Frequencies are exported directly; no estimated foundation eigenvalue is computed.

Digests and evidence fields are exporter declarations. Syntax and comparison consistency are checked; these checks do not prove native completion, convergence, authenticity or correct mode pairing. Review the retained evidence independently. Extra mode labels are preserved; incompatible sets are not compared.

Worked example and reproduction

Run from the repository root. Replace <scratch> with a writable output directory outside the repository. Each command creates the HTML report and the full-precision analyse() result beside it, using the same stem with the suffix .json. Both output paths must be new; existing outputs are never overwritten. The report path must differ from the JSON path. Report frequencies use four significant figures, soil factors retain their supplied values, and loads and relative changes use one decimal place.

python src/digitalmodel/solvers/orcaflex/fixed_bottom_workflow.py \
  --output <scratch>/report.html

python src/digitalmodel/solvers/orcaflex/fixed_bottom_workflow.py \
  --exports tests/solvers/orcaflex/fixtures/fixed_bottom/synthetic_exports.json \
  --soft-factor 0.5 --stiff-factor 2 \
  --output <scratch>/synthetic-example.html

The second command's factors are arbitrary synthetic test inputs, not recommendations. For Fx = −3.0, 0.0, 6.0 kN, the answer is sample mean 1.0 kN and absolute peak 6.0 kN. For Mx = −12.0, 0.0, 24.0 kN.m, sample mean is 4.0 kN.m and absolute peak is 24.0 kN.m. Tower-labelled modal inputs 1.0, 2.0, 3.0 Hz give −50.0% and +50.0% changes. The independent hand calculation is written out in the test docstring. Unprovided turbulent results stay NOT_EVALUATED.

Checks and limits

Run the new test module with pytest and lint both Python files with ruff. Tests cover inventory, source locators, factor selection, missing data, export validation, arithmetic, provenance mismatches, HTML escaping, report generation, exclusive output creation and fresh-process solver isolation. The orcaflex-solver test domain already includes this test directory; no CI selection change is needed.

Missing native runs, defining-reference reconciliation, controller/wind reconciliation, seed policy, mesh/time-step convergence, frequency-separation criteria, soil adequacy, fatigue and structural capacity remain later work. The report follows the repository standard report sections but is a standalone static HTML artifact, not an engine-validated report pack. Share results and method only until vendor redistribution terms have been checked.
