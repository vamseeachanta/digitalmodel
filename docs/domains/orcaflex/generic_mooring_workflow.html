Generic mooring analysis workflow

Summary

The offline workflow enumerates spread and turret arrangements, intact and one-line-damaged conditions, and eight proposed environmental headings: 32 cases. It calculates analytical screens and checks supplied extracted metrics against explicit line capacities and a sourced, condition-specific peak/MBL limit. Missing results or criteria produce NOT_EVALUATED. No licensed integration is imported or executed.

Inputs and provenance

The entry point is digitalmodel.mooring_analysis_workflow. build_case_table(repo_root, damaged_lines) reads the spread and turret base templates under docs/domains/orcaflex/templates/mooring_systems/. Each environmental mapping retains its repository-relative source locator. Proposed headings rotate wave/current together in the template global convention; no template is edited. The source values are generic template assumptions, not sourced site metocean observations.

The case digest covers the exact base-template bytes plus system, condition, heading and selected damaged line. It is a planning-basis digest, not a hash of generated native input. External included component bytes are not covered. Native execution requires a separate complete input manifest. A change to that planning basis invalidates a supplied metric record.

A result record requires basis_sha256, solver_version, source, offset_xy_m and tensions_kn. Every active line must appear exactly once; a removed line must be absent. Offsets are horizontal components relative to the agreed undisplaced vessel reference, in metres; tensions are peak effective line tensions in kN. The caller must establish compatible extraction location, duration and input basis before comparison. A report requires one solver version. Report comparisons are presented to one decimal place; only computed metrics are rounded for display. The input echo retains environmental and analytical inputs without preliminary rounding, preserving small nonzero values. Calculations retain full precision. Malformed records and missing required result fields raise ValueError during assessment. Extracted records are not a substitute for retained native output and are never marked qualified by this module.

Capacities in kN are required for every active line. The criterion is {"ratio": ..., "source": ...}; its source must identify the governing method, edition, clause and condition. A supplied criterion is validated even when results or capacities are absent. The assessment snapshots the criterion so caller mutation cannot replace the ratio or source associated with the calculated result. No API RP 2SK or DNV-OS-E301 numerical limit is assumed. The caller is responsible for the line-capacity source and applicability of the criterion. If either is absent, the check remains NOT_EVALUATED.

An analytical comparison requires a separate screen record with line_id naming an active line, finite nonnegative offset_m and top_tension_kn, a nonempty analytical source, and either a nonempty inputs mapping or a nonempty input_manifest reference. The inputs mapping contains the physical force, stiffness, weight and geometry basis with explicit units and must be finite JSON data. A manifest reference identifies the retained physical-input record; this offline module does not resolve it or verify the physical applicability of either record. Tension differences use the identified line, even when another line has the largest stored tension. The assessment snapshots the screen before checking stored results, retaining its basis even when results or damage selection are missing. The report echoes that record and declares its analytical source separately from the extracted-metric source.

Method and independent worked answer

Offset comparisons use magnitudes only; direction is not compared. Equal magnitudes can therefore give a zero difference despite perpendicular directions. Directional agreement requires a separate vector comparison and is not established by this workflow.

All following input numbers are deliberately invented mathematical examples. They are not component properties, metocean data or engineering criteria.

For a uniform submerged line of weight w, horizontal tension H, fairlead height h above a horizontal touchdown and total length L, the frictionless inextensible equations are:

a = H / w
s² = h² + 2 a h
x = a acosh(1 + h/a)
T = H + w h
R = x + (L - s)

These follow from MoorPy, Catenary.py, ProfileType 2, in the inextensible, zero-friction limit (source header records the 2020 solver update). The existing repository counterpart is src/digitalmodel/orcaflex/mooring_design.py:solve_catenary. The new screen accepts submerged force per length directly and returns unrounded values. It does not use default gravity or material-library coefficients. No external implementation is executed.

With H = 100 kN, w = 1 kN/m, h = 25 m and L = 100 m: a = 100 m; s² = 625 + 5,000 = 5,625 m²; s = 75 m; vertical tension is 75 kN; T = 125 kN. Since acosh(1.25) = ln(2), x = 100 ln(2) m and R = 94.3 m. The screen rejects s > L, which requires a fully suspended geometry solution.

The focused tests cross-check three invented grounded-line cases against the existing repository solve_catenary function, including a small nonzero submerged weight. The comparison converts kN/m to N/m, supplies top pretension T = H + wh, and compares top tension, suspended length, grounded length and anchor radius after the existing function's two-decimal rounding. This checks consistency in the shared analytical regime; it does not establish native solver agreement.

The linear offset screen solves Kq = F. Its basis is the static linear restoring-force relation in OpenStax, University Physics Volume 1 (2016), section 15.1, extended to two coupled horizontal degrees of freedom. A finite symmetric positive-definite matrix is required. Each damaged system needs its own independently established matrix; removing a line is not represented by a default multiplier.

For K = [[4, 1], [1, 3]] kN/m and F = [9, 8] kN, equilibrium gives 4x + y = 9 and x + 3y = 8. Therefore x = 19/11 m and y = 23/11 m, or 1.7 m and 2.1 m for presentation. This is a linear screen, not a nonlinear mooring solution.

For invented line peaks of 40 kN and 80 kN, capacities of 100 kN and 200 kN and a test-only ratio limit of 0.5, the maximum peak/MBL is 0.4 and utilisation is 0.8: PASS against that supplied criterion. An offset [3, 4] m has magnitude 5 m. Relative to a 4 m screen, its signed difference is 100(5 − 4)/4 = 25.0 %. A zero screen leaves the percentage unestablished. A screen tension of 64 kN for the second line compared with its 80 kN stored peak likewise gives 25.0 %. For the first line, the same screen tension compared with its 40 kN stored peak instead gives 100(40 − 64)/64 = −37.5 %, even though the second line governs the stored maximum. The numbers show the arithmetic; they establish no design acceptance.

Runnable worked example

Run from the repository root with its Python dependencies installed. Set MOORING_REPORT_DIR to an existing approved scratch directory. The example creates only derived files there and refuses to overwrite existing files. The generated report shows one synthetic metric record and 31 cases without results; no capacity criterion or native qualification is established; the printed analytical answers are independent of licensed software.

PYTHONPATH=src python3 - <<'PY'
import json
import os
from pathlib import Path
from digitalmodel.mooring_analysis_workflow import (
    assess_case, build_case_table, catenary_screen, linear_offset, render_report,
)
cases = build_case_table(Path.cwd(), {
    "spread": "Mooring_L1", "turret": "Mooring_L1",
})
print("Top tension [kN]:", catenary_screen(100, 1, 25, 100)["top_tension_kn"])
print("Linear offset [m]:", tuple(round(v, 1) for v in
    linear_offset((9, 8), ((4, 1), (1, 3)))))
case = cases[0]
physical_inputs = {
    "catenary": {"horizontal_kn": 40, "weight_kn_m": 1, "height_m": 24, "length_m": 100},
    "linear_offset": {"force_xy_kn": [4, 0], "stiffness_kn_m": [[1, 0], [0, 1]]},
}
line_screen = catenary_screen(**physical_inputs["catenary"])
offset_xy = linear_offset(**physical_inputs["linear_offset"])
screen = {
    "line_id": "Mooring_L1",
    "offset_m": (offset_xy[0] ** 2 + offset_xy[1] ** 2) ** 0.5,
    "top_tension_kn": line_screen["top_tension_kn"],
    "source": line_screen["source"] + "; OpenStax linear restoring force, section 15.1",
    "inputs": physical_inputs,
}
result = {
    "basis_sha256": case["basis_sha256"],
    "solver_version": "example-only",
    "source": "synthetic arithmetic; not native results",
    "offset_xy_m": [3, 4],
    "tensions_kn": {name: (80 if name == "Mooring_L2" else 40)
                    for name in case["active_lines"]},
}
assessment = assess_case(case, result, screen=screen)
assert assessment["offset_difference_pct"] == 25
assert assessment["tension_difference_pct"] == -37.5
assert assessment["screen"] == screen
output = Path(os.environ["MOORING_REPORT_DIR"])
artifacts = {
    "mooring-cases.json": json.dumps(cases, indent=2),
    "mooring-analysis.html": render_report(
        cases, {case["case_id"]: assessment}, revision="03", date="2026-10-21"),
}
for name, content in artifacts.items():
    target = output / name
    with target.open("x", encoding="utf-8") as stream:
        stream.write(content)
    assert target.read_text(encoding="utf-8") == content
