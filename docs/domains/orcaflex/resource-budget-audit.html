OrcaFlex resource declaration audit

Summary

The source inventory identifies native-model constructor candidates and worker-pool declarations without importing the inspected modules. No runtime budget is established. The governing finding is that a pool's worker count alone cannot establish native thread demand: the vendor documents processing-core defaults when threadCount is omitted.

Across these roots, 46 model-call candidates declare no explicit thread count, 13 declare a positive integer literal, and one has unresolved expanded arguments. All inventory budgets are NOT_EVALUATED. These are syntactic categories: a candidate is not proof of an OrcFxAPI binding.

Both optimized parallel analysis implementations construct models with omitted native thread arguments and declare separate executor pools. The regular parallel-analysis leaf instead forwards conditional expanded arguments; that call remains unresolved by static inspection. The batch workflow supplies a thread setting to that leaf. These observations do not establish runtime readback or total CPU use.

Each command emits JSON to standard output and exits nonzero on parse/read errors. The normal package dependencies are required when using module execution. The same file also supports direct Python execution without importing the package initializer.

Explicit resource accounting

evaluate_budget(workers, threads_per_model, cpu_budget) evaluates a homogeneous configuration with explicitly supplied positive integer counts. Missing inputs give NOT_EVALUATED. No processing-core count, reserve fraction or licence limit is inferred.

requested_threads = workers × threads_per_model
WITHIN_BUDGET if requested_threads ≤ cpu_budget
EXCEEDS_BUDGET otherwise

This is an exact accounting identity, obtained by summing the same configured thread count for each worker; it is not an empirical engineering formula or performance model. An independent test example enumerates four workers reserving three threads each as [3, 3, 3, 3], summing to twelve against eight supplied CPU slots. The CPU-slot count is a synthetic test input, not an acceptance limit for a real installation.

Interpretation and limits

  • scope_operations reports recognized method names in the same lexical scope. Simulation, extraction and conversion evidence may coexist; no exclusive operation classification is inferred.
  • Attribute calls named Model, direct OrcFxAPI Model imports and recognized pools are candidates. Binding shadowing, reassignments, wrappers, arbitrary factory aliases and indirect calls are not resolved.
  • Methods called on different objects in the same scope may contribute operation evidence. An empty operation list means unclassified, not idle or non-simulation.
  • Constructor arguments do not establish post-load settings, property mutations, native readback, simultaneous active models, process-tree threads, CPU affinity, memory demand, licences or throughput.
  • Expanded arguments, computed expressions and existing-model handles remain unresolved. Symlinks are skipped. Digests identify the source bytes read; filesystem changes during traversal are not an atomic snapshot.

Way forward

The next change should establish explicit per-workflow contracts, associate each pool with its model-producing leaf, and verify native requested/observed thread counts without changing engineering inputs. Native execution and runtime policy changes remain outside this audit. Tracking: issue 2130.
