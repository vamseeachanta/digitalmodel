Solver retrieval and export evidence gates

Summary

The provider-neutral digitalmodel.infrastructure.solver_evidence API checks supplied retrieval metadata, keyed records and decimal representations. A PASS applies only to the named gate and its supplied policy. Native provenance, stored-result precision, engineering acceptance and adapter adoption are not established. No engineering tolerance is supplied by this module.

Scope and implementation slices

  1. Retrieval validity: explicit case, active result set, recovery source, frame, response unit and coordinate unit; complete keyed records; coordinate comparison; separate unavailable, invalid and numerically failed states.
  2. Export precision: exact decimal parsing, a last-place rounding bound and a caller-selected known formatting witness.
  3. Independent readback: complete matching keys and result identity, distinct capture identifiers, and fixed subfloor precision/readback limits.

The API does not select recovery sources, convert units, invoke solvers, read files, repair inputs or change the signed-residual acceptance operators. Inputs must be frozen before a comparison. A source citation is an attributed claim supplied by the caller; its authority and suitability require separate review.

Retrieval contract

check_retrieval takes a RetrievalEnvelope, an expected EvidenceIdentity, an explicit sequence of ExpectedRecord objects, a coordinate tolerance and its criterion source. Expected records must be nonempty, uniquely keyed by the pair (entity/station, component), and carry nonempty coordinate tuples. Each coordinate tuple must use the declared coordinate unit and frame. Each response uses the declared response unit. Automatic/default recovery-source labels are refused. Adapters must record the actual selected source and active set, rather than copying requested settings into observed metadata.

Coverage requires equality of observed and expected key sets, with duplicates refused before constructing a map. Each coordinate dimension is checked by abs(observed - expected) <= coordinate_tolerance. Coordinates are identity checks; their printed precision requires adapter-specific checks. No default tolerance or unit conversion is inferred.

Decimal precision basis

The paper What Every Computer Scientist Should Know About Floating-Point Arithmetic (1991), section Relative Error and Ulps, gives the half-unit-last-place bound for rounding to nearest. For a decimal mantissa with d fractional places and an explicit exponent e (zero if absent), the implemented bound is

half_quantum = 10^(e - d) / 2

The decimal radix and factor one-half follow from the printed decimal place and the cited nearest-rounding bound. This is a bound on representation rounding, not a bound on source arithmetic, discretization error or native storage error. Truncation and unknown rounding modes do not satisfy the assumption; their adapter must refuse this gate until a reviewed representation contract is supplied.

Independent hand calculation: 1.234E+2 = 123.4 = 617/5 has last place 0.1 and half quantum 0.05 = 1/20. Likewise 0.000E+0 has half quantum 0.0005 = 1/2000; 0E+0 has half quantum 0.5 despite having the same numeric zero. Negative signs do not change the quantum. All examples are mathematical fixtures, with no engineering acceptance limit implied.

Exact decimal string construction and rational arithmetic avoid dependence on ambient Decimal precision, rounding, exponent bounds or traps. Floating-point inputs, nonfinite values, whitespace, underscores, non-ASCII digits, solver-specific exponents and overflow markers are refused. A native parser must perform any source-backed format normalization before calling the helper.

Representation limits

This revision sets software resource bounds of 128 characters per decimal literal and an absolute explicit exponent of at most 1000. These are implementation limits, not engineering constants or acceptance criteria. A format outside this bounded representation requires a reviewed contract change; its values are not silently clipped.

Precision and readback contract

PrecisionPolicy requires a response unit, positive dimensional floor, positive maximum half quantum, nonnegative absolute readback limit and criterion source. Both budgets must be strictly below the dimensional floor. The budget magnitudes require a justified caller criterion; being below the floor alone does not establish suitability. The module supplies no stress, displacement or relative-error constants.

check_export_precision requires exact expected keys, matching export, readback and expected identities, and a policy unit equal to the response unit. Export and listing half quanta must each be at most the fixed precision budget. For every key, abs(export - readback) <= readback_limit is required. A formatting witness must equal its predeclared exact value and meet its separate caller-supplied half-quantum budget. A mismatch is INVALID_EVIDENCE, not an engineering numerical failure. An absent capture or witness is NOT_EVALUATED.

Mappings are accepted only after native duplicate-key refusal. Different capture identifiers are required, and the same mapping object cannot serve as its own readback. Distinct labels alone do not prove independent retrieval. Adapters must retain the independent native captures, verify their attribution and prevent copied or relabeled exports from becoming independent evidence. No JSON decoding or repair is performed here; duplicate JSON fields and byte-order marks require refusal at ingestion.

Caller sequence

  1. Freeze the expected identity, station/component inventory, sourced limits, rounding contract, formatting witness and warning/reference-disagreement policy.
  2. Retain byte-exact native evidence and source-specific configuration/status, including stored-result precision before and after result creation. Verify its provenance and distinguish absent stream capture from a retained empty stream.
  3. Parse source-specific records without discarding duplicates, missing-value indicators or diagnostic state. Call check_retrieval.
  4. When retrieval passes, call check_export_precision with independently attributed, matching export/listing captures. The response unit and coordinate unit remain explicit; no conversion or contribution averaging is performed.
  5. Expose each gate status. Perform engineering comparisons only after all separate required gates are established. PASS for these helpers does not replace storage precision, diagnostic, provenance, reference or engineering criteria.

Verification and remaining work

Refusal-first tests in tests/infrastructure/test_solver_evidence.py cover unavailable/defaulted results, positive and negative readback mismatches, key coverage, coordinate boundaries, result/source/frame/unit attribution, coarse zero representations, formatting witnesses and hostile Decimal context. Expected numbers are independent hand calculations in the tests, with illustrative caller-supplied limits. No native solve or measured dataset is used.

Later slices will address native storage-configuration evidence, authenticated capture provenance, exact-byte review receipts, source-specific diagnostic policy, reference-disagreement disposition and reviewed adapter integration. Existing signed-residual work remains separate. Independent provider review of these exact artifacts is pending; no independent review verdict is claimed.
